# App Store claim verification

Run from any checkout of the integrated build to be uploaded:

```sh
python3 script/claims/run.py all --dd /Volumes/Studio/Development/Caches/b7-claims/DD --output /Users/roshansilva/Documents/Codex/2026-10-01/perf-push/b7-claims
```

The runner creates timestamped source scans, Xcode settings, command logs, JSON exit receipts and simulator `.xcresult` bundles. It builds the isolated Mac companion for architecture/minimum-OS inspection but never launches/installs it and never targets a real device. Native commands use the canonical `~/bin/farside-lock` first-free-slot helper, verified to preserve both locks with `/usr/bin/lockf -k`; default simulator lookup/create stays serialized under the primary lock. Explicit UUID validation is read-only and may precede taking the other free slot. At most the two approved slots are used. It waits for PAUSE-BUILDS, PRIORITY-BUILD and QUIET-GRANTED-* before each build/test, checks them again after acquiring `lockf -k`, keeps package resolution pinned, and refuses builds below 10 GiB internal free disk. It uses Debug because the lane rules require it; Release effective shipping-host settings are separately audited; source config mapping covers phone, watchdog and preserved legacy targets. The uploaded Release build still needs integration/release and physical acceptance.

Stages `auto`, `settings`, `build`, `phone`, `ipad`, `duo`, `core`, `backend`, `host` can be rerun separately. `phone`/`ipad` require a successful `build` on the **same source**, DD and test binary. The runner hashes source before/after compilation, binds complete app/test bundles (including debug dylibs and resources), and rechecks identity under the shared lock before and after testing. Simulator cleanup stays under that lock. Stop and rebuild after integration; never apply an old `.xcresult` to a changed build. `--phone`, `--ipad`, `--duo` override explicitly lane-owned simulator UUIDs. By default the runner creates/reuses dedicated `Farside B7 Claims phone` (iPhone17/iOS27.0) and `Farside B7 Claims ipad` (iPad miniA17 Pro/iOS27.0) simulators. Explicit overrides must be lane-owned. The shared C643 phone was concurrently targeted by a b8 lane on2October, interrupting a claim audit; that run is retained as partial raw evidence, not accepted whole-stage proof. Dedicated names keep the default checks separate from other lanes. Lookup/create is serialized under the shared lock and reused device types are validated. Under-lock preflight rejects an already-targeted simulator without launching or shutting it down; cleanup rechecks literal UUID destination conflicts and invalidates the receipt rather than shutting down a newly colliding device. Exclusive ownership remains required because another uncooperative runner can still start between checks. Do not substitute another lane's active simulator. The one Duo attempt is bounded to 180 seconds and is not retried; a terminal migration failure is rejected even if simctl exits zero. Backend renewal/route checks use only local Cloudflare fixtures and matching shared lockfile dependencies, never deployment/provider actions. Every simulator run shuts down its explicitly assigned simulator, never all simulators.

Claim UI tests live in the existing `RemotePhoneUITests/FarsideRedesignUITests.swift` file, so source membership needs no project regeneration. Offline fixtures do not pair or contact a real Mac. Audit callbacks collect all reported issues, attach screen/hierarchy reports, and assert zero issues after enumeration; an audit test failure is expected when issues are present. Inspect findings by screen; do not suppress contrast/hit-region/Dynamic Type failures merely to get green tests. Simulator gesture generation and preview text do not prove hardware haptic feel, microphone transcription, actual remote key delivery, PiP thumbnails, or physical fold alignment.

`phone-more` and `ipad-more` select only the two supplemental Home-utilities accessibility methods, after a fresh `build` containing them. They allow extending the original frozen audit without repeating its 55 fixtures. After the supplement is integrated, normal `phone` and `ipad` select the original eight claims methods: 55 original fixtures plus nine Home/menu surfaces, at default and AX-XXXL on each platform. UI runs also wait for `CHAIN2-GO` outside the lock and release/retry if it closes before execution. Summary/test-tree JSON and text attachments are exported after failing audits as well as passes. Supplemental acceptance requires both named methods to execute and pass; empty or skipped selections fail the runner. Both default and maximum per-method time allowances default to7200seconds (`--ui-timeout`), increased after the fresh phone sweep required2225seconds for28/55 fixtures; the existing phone run retains its captured3600seconds. The maximum alone leaves XCTest's ten-minute default and can truncate the large inventory. Audit coverage is bounded to visible initial/scrolled slices; recorded missing markers or navigation failures prevent a surface from being considered reached. Actual VoiceOver navigation, OS permission alerts, camera scanning, enabled wake confirmation, purchase/provider flows, and live remote-desktop semantics remain separate gates. Reconcile this inventory with deliberately removed or added screens on each integrated build.

Core C4/C5 source/test/harness limitations and the scoped test selection are in `HOST-AUDIT.md` in the output folder. A standalone media bench is not a no-session-cap test. No >=35-minute actual native session was run by this lane; see the hands checklist.

Pass/fail results update evidence, not nomination/ASC settings. Keep `CLAIMS-MATRIX.md`, `CLAIMS-VERDICT.md` and `HANDS-CHECKLIST.md` with the exact integrated commit and uploaded build receipt before public claim changes.

Exit75 is reserved for pre-execution lock/gate refusal. A native command returning75 after execution is mapped to80, preventing the canonical helper from repeating an already-executed action.

Recovery stages `phone-audit` / `ipad-audit` select bounded accessibility methods after a fresh same-source `build`. They run all nine groups at both sizes by default: `entry`7, `session`11, `help`6, `coach`6, `display`1, `settings`9, `errors1`8, `errors2`7, and `home`9. The first eight partition the original55 fixtures; Home adds the existing nine surfaces. Full recovery is18 selected audit methods and64 surfaces per size/platform. Use `--audit-groups display,settings,errors1,errors2 --audit-size AX-XXXL` for a partial rerun; its scope receipt names only those groups/sizes. Display remains portrait and retains the quiet input probe/two seeded displays: phone navigates Controls → Display; iPad navigates Controls → Settings → Display. Neither route selects a display or sends a remote action.

`phone-features` / `ipad-features` select exactly six existing UI methods: four coach/pinch/keyboard/privacy claim methods plus the keyboard-bar and nonrecording voice-preview layout tests. They perform no accessibility inventory sweep and cannot prove C8 or whole-app completion. `phone-units` selects the exact89 existing methods in ten phone-unit classes with the same source/artifact guard and separate exact-selection receipt; it can be rerun without an audit. All recovery modes require every exact selected Class/method to execute and pass, with zero skipped/failed/unexpected cases. Failed audits retain all findings and their failed command result. Planned/completed group inventories, raw results and screenshots remain the evidence for partial coverage when a snapshot exception prevents completion.

Normal `phone` / `ipad` explicitly select the original eight claims methods plus their existing extras, so new bounded methods do not silently duplicate those sweeps or turn an old failed class into a pass. Future `all` builds, then uses the combined `phone-check` / `ipad-check` stages; it always covers all groups/both sizes. Recovery group/size filters apply only to `phone-audit` / `ipad-audit`. It retains every command/guard result and does not convert an earlier failed monolithic method into a pass. Use separate recovery stages after a fresh compile; this lane's exhausted one-attempt Duo allowance still forbids repeating `all` here. Audit diagnostics retain one initial hierarchy per fixture (including accessible controls), every initial/scrolled screenshot, and every unfiltered `.all` issue's type/compact/detailed description. They omit repeated per-control field queries and per-issue element snapshots. Actual VoiceOver/device acceptance remains separate.

New raw log directories live at `<DD parent>/receipts/<timestamp>` on the SSD; `<output>/logs/<timestamp>` is a symlink preserving public receipt paths. The runner requires `/Volumes/Studio` to be an actual mounted volume and DD to resolve beneath it before creating storage or starting commands. Unmounting the SSD makes those receipt links unavailable; keep the physical receipt directories with the report. Existing receipt directories are never overwritten or deleted. Simulator/device data remains on the internal disk, and the10GiB internal floor still applies.

`phone-check` combines89 phone-unit +18 bounded audit +6 feature/UI methods in **one native invocation (113 distinct Class/methods)**. `ipad-check` combines18 audits +6 feature/UI methods (**24 distinct methods**). They always select all nine groups/both sizes; partial filters remain for the separate audit stages. Unit-class selectors use `RemotePhoneTests`, and all three UI-class selectors use `RemotePhoneUITests`. These stages share exact selection, source/artifact, gate, conflict, shutdown and export guards. A failed or skipped audit method makes the combined acceptance fail; counts describe selected coverage, not zero findings or a completed original eight-method run. The existing individual stages remain available. The10GiB floor is checked before the combined native invocation; combining avoids extra native starts/gate checks after the device boot increases internal data.
