## 2. Clipboard sync (text, user-initiated both ways)

### Behaviour
- **Paste to Mac** — the system paste control (keyboard toolbar, and a row in Controls › Clipboard) hands PocketDesk the iPhone text. The phone chunks it, the Mac verifies the whole transfer, writes `NSPasteboard.general`, and acknowledges `stored`. Only after that acknowledgment does the phone press **⌘V** through the normal admitted key path (fresh picture + host token), if “Press ⌘V after sending” is on (default on). Toast: “Pasted on your Mac” / “Copied to your Mac’s clipboard” / “On your Mac’s clipboard. Press ⌘V on the Mac to paste.”
- **Copy from Mac** (`doc.on.doc` in the keyboard toolbar; “Copy selection” in Controls) — presses **⌘C** on the Mac, then asks for the clipboard with `afterCopy`. The host recorded `changeCount` *before* posting that ⌘C and waits up to 1.2 s for it to change, so the phone never receives the previous item; no change → “Nothing new was copied. Select text on your Mac first.”
- **Get Mac clipboard** (Controls) — returns whatever is already on the Mac clipboard.
- Result is always visible: an in-session glass toast (auto-hides, tap to dismiss, VoiceOver announcement, success/warning haptic) and a status line in the Controls sheet. Contents are never displayed, logged or echoed; messages contain only character counts.

### Automatic Mac→phone on ⌘C — designed, deliberately narrow
Automatic transfer happens only for the phone’s *own* Copy command (one user gesture, two halves). PocketDesk never watches the Mac pasteboard (`changeCount` polling) and never pushes Mac-local ⌘C copies to the phone. PRODUCT §8 rules out “automatic clipboard upload”; monitoring would need an explicit opt-in, a visible indicator on both devices, the same concealed-type filter and a product decision. Recommendation: keep it off the roadmap until users ask.

### Protocol (backward compatible, appended only)
- `RemoteAction` gains two optional fields at the end: `clipboard: ClipboardFrame?`, `features: [String]?`, plus one line at the top of `validate()` that delegates to `validateSessionExtension()` (in `SessionContinuity.swift`). Existing fields, actions and validation are untouched.
- New action names: `clipboard`, `pause`, `resume`.
- **Negotiation:** the host appends `features: ["clipboard.text.1", "pause.1"]` to its periodic `capture` status. Old phones ignore the unknown key (tested with a legacy decoder). New phones send extension actions only after seeing the feature, because an old host’s validator rejects unknown action names and would end the session. The host never sends a clipboard frame unprompted, so old phones never see one.
- `ClipboardFrame`: `op` ∈ push/pull/data/result, `transfer` (8–32 alphanumerics), `kind` text/url, `index`/`count`/`bytes`, SHA-256 `digest`, `data` chunk, `status`, `afterCopy`. Status codes travel as strings so a newer peer’s unknown code degrades to a generic failure instead of a decode failure.

### Limits, framing, pacing
| Parameter | Value | Why |
|---|---|---|
| Max size | 256 KiB UTF-8 | Covers code/log snippets; 64 chunks |
| Chunk | 4 KiB raw | base64 + worst-case JSON `\/` escaping + envelope stays < 16 KiB control-message bound (tested with all-`0xFF` data) |
| Pacing | ≤2 chunks per 10 ms tick, only while `bufferedAmount` < 16 KiB | Input shares the ordered channel; `PeerMedia.sendControl` refuses above 64 KiB and the coordinator treats that as a disconnect |
| Integrity | in-order only, digest + exact length + valid UTF-8 before any pasteboard write | nothing partial is ever written |
| Timeouts | Mac reassembly 5 s idle; Mac read 12 s → `busy`; phone send 8 s → “Delivery is uncertain”; phone receive 15 s | never a silent hang |
| Concurrency | one transfer per direction; second request → `busy` | bounded state |

### Never block, never leak
- All `NSPasteboard` access runs on one serial utility queue (`HostClipboardService`), never the main thread. A lazily provided item or a future macOS paste-privacy alert therefore cannot freeze input injection — which is what would let the remote user reach that alert on the Mac and click Allow. A read that outlives its timeout is discarded.
- `accessBehavior == .alwaysDeny` → `denied` without reading. Types (metadata) are checked first; any concealed/transient/auto-generated marker → `concealed`, contents never read. Unit-tested against real, uniquely named pasteboards.
- Items PocketDesk writes carry `org.nspasteboard.source` and a private `com.roshan.pocketdesk.remote-clipboard` marker (loop protection for any future sync).
- Authorization: host accepts clipboard frames only in the current authenticated session and epoch, not while paused, and only with **effective control** (Allow control + Accessibility) — the same state the phone shows as “Controlling”. Revoking control cancels in-flight transfers. The browser route cannot reach it (its input gate has its own action allowlist).
- iPhone reads happen only through the system paste control; iPhone writes are `.localOnly`.

## 3. Staying connected in the background

### What iOS legitimately allows
Only the finite task-completion window. PocketDesk uses it to (1) release input and pause video immediately, (2) keep the authenticated peer alive for a quick app switch, and (3) close the transport cleanly before suspension so the relay frees the phone’s slot. No audio, VoIP, location or PiP background mode is used.

### Phone state machine (`BackgroundContinuity`, pure and unit-tested)
| Event | Behaviour |
|---|---|
| `.inactive` (Control Center, banners) | unchanged: shield picture, cancel held input, session kept. If connected, request the background task now (Apple: begin early). Returning to `.active` ends it. |
| `.background`, connected, host has `pause.1`, task granted | Conceal (overlay covers the whole session view; the video surface is removed so no Metal work or pixels in the snapshot), release input, drop input readiness (fresh/capture/token), cancel clipboard work, send `pause`, **hold** for `min(25 s, remaining − 5 s)`. |
| hold ends (timer / expiry handler / transport lost) | `release()` + `connection.stop()` — a clean relay close so the slot frees at once; retries are suppressed while backgrounded. |
| `.background`, anything else (old host, no task, connecting) | Close cleanly now; resume on return. |
| Return while still connected | Send `resume`; un-conceal immediately; viewport/zoom preserved. Input stays disabled until the host’s new epoch, a fresh frame and capture health arrive. Watchdog: no host status within 5 s → automatic fresh reconnect. |
| Return after the session closed, ≤15 min | Automatic reconnect with cached credentials (no pairing), “Reconnecting…” card with Cancel; the picture appears only after authentication. Failure → “Couldn’t reconnect” with Reconnect / Return. |
| Return after >15 min | “Session ended” card with Reconnect (explicit choice). |
| Nothing was open | Snapshot concealed; return goes straight home. |

### Host (`HostPhonePause`)
`pause` (current epoch only): release held input, expire input tokens, stop ScreenCaptureKit capture (saves Mac CPU/GPU and all video bandwidth), stop capture-health messages, cancel clipboard work — but keep the peer and session slot. `resume`: re-run `beginCapture()` → new input epoch, geometry and capture, so no pre-background input can apply. No `resume` within **45 s** (longer than the phone’s maximum hold) → `RemoteCoordinator.dropPeerSession()` ends only that phone session; the host stays registered for its paired phone. Tested over the real local relay: the phone rejoins with cached trust, no approval prompt.

### Compatibility
New phone + old host: no `pause.1` → phone closes on background and auto-reconnects on return (still better than today). Old phone + new host: never sends `pause`, behaves exactly as before.

## 3b. Display sleep, lock and Mac availability (host)

Before: `screensDidSleep` stopped sharing, so an awake Mac whose display had merely slept was unreachable from the phone. That same teardown was also the only thing that stopped sharing when the Mac was *locked* (lock → display sleep), and after a wake sharing restarted even if the Mac was still locked.

| Event | New host behaviour |
|---|---|
| Display sleeps (system awake) | Sharing and relay presence stay up. With a phone connected: remote input released, capture status carries `hostState: "displayAsleep"`; the phone shows “Your Mac’s display is asleep” with **Wake display** (new `wake` action, feature `display.wake.1`, needs effective control). |
| Phone connects / resumes while the display sleeps | `IOPMAssertionDeclareUserActivity(…, kIOPMUserActiveRemote)` wakes the display before capture starts (no special privileges, per `IOPMLib.h`). |
| System will sleep · fast user switch · **screen lock** | Input and capture stop immediately, the phone receives `hostState` `sleeping` / `switchedUser` / `locked` on the ordered channel, and sharing tears down 0.2 s later. The phone then says “Your Mac went to sleep at 3:14 PM…” / “…was locked… unlock it in person” instead of guessing (PRODUCT: only state what the Mac reported). |
| Lock detection | `com.apple.screenIsLocked` / `…Unlocked` distributed notifications (widely used, undocumented names) plus a 1 s `CGSessionCopyCurrentDictionary()["CGSSessionScreenIsLocked"]` check, and a hard check before any capture starts. Wake/unlock resumes only if the session is not still locked. |
| Power | While sharing (and Keep awake on): `kIOPMAssertPreventUserIdleSystemSleep` keeps the Mac reachable; the display assertion is held only while a phone is connected and not paused. Lid close, Apple-menu sleep and low battery still sleep the Mac (documented assertion limits). Strictly less power than before, when the display assertion was held for the whole sharing period. |

Pure policies (`HostSleepPolicy`, `HostPowerPolicy`, `HostScreenLock.isLocked`) are unit-tested; the notification wiring, the real display wake and lock detection need the physical checks below. Not done: AC-only/battery policy, screen-saver detection, LAN wake (research gap 3 items 5.1–5.2), and a host-UI line for “display asleep”.

## 6. Physical test checklist (iPhone + Mac, disposable text only)

Clipboard
1. On the iPhone copy a sentence with an emoji. In a Mac text field, open the keyboard bar, tap the paste control. Expect no iOS paste prompt, text appears, toast “Pasted on your Mac”.
2. Turn off “Press ⌘V after sending”, repeat; expect only the Mac clipboard to change (⌘V on the Mac pastes it).
3. Select text on the Mac, tap Copy (`doc.on.doc`). Expect “Copied from your Mac · N characters”; paste in Notes on the iPhone. Try with nothing selected → “Nothing new was copied…”.
4. Copy a password from 1Password or the Passwords app on the Mac, then Controls › Get Mac clipboard → “…password or private item…”, iPhone clipboard unchanged.
5. Send ~200 KB of text while moving the pointer: pointer stays responsive; >256 KB is refused with the limit message.
6. Turn off Allow control on the Mac → clipboard actions disabled/refused.
7. If macOS shows a paste-privacy alert on the Mac, confirm the pointer still works and you can click Allow remotely.

Background
8. In a session, switch to another app for ~5 s and return: screen appears within ~1 s without a reconnect card; zoom/pan kept; input works once the picture is fresh.
9. App switcher while in session: snapshot shows “Screen hidden”, never Mac pixels.
10. Start a drag (hold), then swipe home: the Mac releases the button immediately.
11. Background for ~60 s (past the hold): return shows “Reconnecting…” then the live screen; no pairing or Mac approval.
12. Lock the phone for 20 minutes: return shows “Session ended” with Reconnect.
13. While backgrounded, watch the Mac: capture stops at once (no streaming CPU), and the menu bar returns to ready when the phone’s hold ends (~25 s) — or within 45 s at most if the phone never closed cleanly.
14. Repeat 8 and 11 on cellular through the relay once it is deployed.

Display sleep and lock (Mac)
15. With sharing on and no phone connected, let the Mac display sleep (or press ⌃⇧⏏ / use a hot corner). Connect from the phone: the display wakes and the picture appears; the Mac never went to “stopped”.
16. During a session, sleep the display: the phone shows “Your Mac’s display is asleep” and Wake display brings the picture back.
17. Lock the Mac (⌃⌘Q) during a session: the phone's input stops at once, the session ends, and the phone says the Mac was locked. Confirm no lock-screen frames are streamed afterwards, and sharing resumes by itself after unlocking.
18. Apple menu › Sleep during a session: the phone says the Mac went to sleep; after wake with a password-protected lock screen, sharing stays off until unlock.
19. Leave the Mac idle past its system-sleep time with sharing on: it stays reachable while the display sleeps (Activity Monitor › Energy shows the “PocketDesk remote access” assertion); turning off Keep awake lets it sleep normally.

## 7. Open risks and follow-ups

- **Actual hold length and socket survival on device are unmeasured.** iOS grants an undocumented, variable window; the code adapts to `backgroundTimeRemaining`, but the relay WebSocket or ICE may still drop earlier on some networks.
- **Video after resume:** capture restarts with a new epoch; the encoder may send a delta frame first and the iPhone’s VideoToolbox session may have been invalidated in the background. WebRTC should request a keyframe on decode errors — verify step 8 shows a clean picture quickly; if not, force a keyframe on resume.
- **Relay slot:** clean close frees it immediately; if iOS suspends the app before the close is flushed (1 s grace is kept on the task), the server’s 60 s idle timeout applies and reconnect falls back to the existing bounded retries.
- **Mac-side transparency:** the host UI does not yet say “phone paused” or “clipboard sent to phone”. Consider a subtle menu-bar status line.
- **Merge with the pointer-telemetry work:** both branches append to `RemoteAction`. Extension actions return early from `validate()`, so any new telemetry field should also be rejected on `clipboard`/`pause`/`resume` in `validateSessionExtension()` after merge.
- **PasteButton styling** is system-controlled (tinted circle in the toolbar); confirm it reads well in both themes and doesn’t show a prompt.
- **Keyboard row order:** Paste/Copy now lead the scrolling key row, which pushes ⌘ just past the right edge in portrait. Judge on the phone; the alternative is to move the pair after Return (less discoverable).
- **Lock detection relies on undocumented notification names** plus the `CGSSessionScreenIsLocked` session key; both are widely used but not API contracts. The pre-capture check fails closed only if the key is present.
- **Wake on connect is deliberate:** a phone connection now turns the Mac display on (as Workbench does). That lights the local screen for anyone nearby; privacy-curtain work stays separate.
- iPhone passwords copied from the iOS Passwords app carry no marker PocketDesk can see through the paste control; sending them is always an explicit user tap.
- PRODUCT.md, the implementation ledger and the Workbench matrix (“Clipboard sync ❌”, “Background connection persistence ❌”) should be updated by the integrating agent after physical checks.
