# PocketDesk encoder strategy: learn from LIQUID without rebuilding it for launch

**Research/design only — 28 September 2026.** Scope: MacBook Air M4 host, iPhone 17 native viewer, macOS/iOS 26 deployment floor, conditional 17 November launch. This report proposes experiments; it does not change [PRODUCT.md](../../../PRODUCT.md), the code, or the launch criteria. External sources below were checked on 28 September 2026. Vendor performance statements are claims, not PocketDesk measurements.

## Decision

**Do not build a fully custom LIQUID-like encoder and transport for launch.** A same-day local loopback has now identified and repaired a severe H.264 level mismatch in that test; the physical phone's earlier 15–28 distinct updates/s and 117 ms p90 gap still need a fresh run. Verify the improved hardware-video path on the phone, then add a bounded lossless dirty-region *text/UI overlay* only if sharpness or local response remains inadequate after that measurement. The overlay is the smallest defensible piece of a custom screen codec. Keep H.264 as the browser and device compatibility floor. HEVC is a native-client experiment, not an assumed WebRTC switch. A complete tile codec plus congestion control, internet traversal, relay and browser implementation is a separate post-launch research program.

This recommendation follows the task's observed phone result, recorded in [the Workbench benchmark](../../BENCHMARK-WORKBENCH-2026-09-28.md), not a proven encoder bottleneck. Capture cadence, `pushFrame` lock drops, WebRTC adaptation, encoder time, packet loss, receiver jitter buffering, Metal presentation and display refresh can all create the same visible gap. A better codec can improve byte cost or text fidelity and still leave lag untouched if capture or presentation dominates. Astropad's “often under 16 ms end-to-end” is a [vendor claim](https://astropad.com/blog/liquid/) with an unspecified measurement method and local-network conditions; it is not a launch target for the current pipeline.

## What PocketDesk actually does today

`RemoteCapture.swift` sets a 1/60-second **minimum** frame interval, queue depth 3, video-range NV12 (`420YpCbCr8BiPlanarVideoRange`), selected quality dimensions, and captured cursor. It forwards only `.complete` sample buffers and periodically resends the last buffer when the source reports healthy idle status. It does not read `SCStreamFrameInfo.dirtyRects`. The desired interval is a throttle, not a guarantee of 60 unique updates; [Apple's ScreenCaptureKit sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos) illustrates the same distinction and explains queue depth's memory/throughput trade-off. `PeerMedia.swift` wraps each buffer as `RTCCVPixelBuffer`, takes a nonblocking capture lock (which can drop a frame), and passes it into a screen-cast `RTCVideoSource`. **Before the same-day streaming change**, it used `RTCDefaultVideoEncoderFactory`, merely preferring the first advertised `H264` codec. The in-progress native path now uses `PocketDeskVideoEncoderFactory`/`PocketDeskVideoDecoderFactory` to advertise H.264 level 5.2 while the browser path retains the compatible factory; its live device behavior is pending. The phone displays an `RTCMTLVideoView` in `RemotePhoneApp.swift`. Installed `Package.resolved` pins the [stasel binary WebRTC package](https://github.com/stasel/WebRTC) at **153.0.0**, revision `4266157cd08f92115de885ab12d87196a8db87e1`.

That establishes an H.264 preference and a 4:2:0 capture source, not the encoder selected at runtime, a particular VT rate-control mode, or phone decode/presentation latency. A same-day **pre-change synthetic local loopback** receipt in `.claude/worktrees/agent-a14ff0dc60d0399e2/outputs/bench/baseline.log` provides stronger diagnosis for that test: at 2940×1912 it negotiated H.264 High/Baseline **level 3.1**, logged a maximum allowed **4 fps**, created a hardware-accelerated VT session, then failed H.264 encode with **-12902** and switched to software VP8/libvpx at about **3 encoded fps**. The 1920×1248 case logged an 11 fps cap and the same encode failure. Thus hardware session creation is not successful hardware *encoding*. This is a concrete local-loopback fault, not proof that the physical phone's earlier 15–28 updates/s had exactly the same cause. Upstream WebRTC's [Objective-C default encoder factory source](https://webrtc.googlesource.com/src/+/20967ac1956e9d4ba4552af3ee7727e920aabc78/sdk/objc/components/video_codec/RTCDefaultVideoEncoderFactory.m) lists H.264, VP8, VP9 and conditional AV1, with no HEVC in that snapshot. Its [H.264 VideoToolbox implementation](https://webrtc.googlesource.com/src/+/27af5db5e08034ac8432bfa263edec29afe471cc/sdk/objc/Framework/Classes/VideoToolbox/RTCVideoEncoderH264.mm) sets `RealTime` and disables frame reordering, yet comments that a `MaxFrameDelayCount=1` setting failed in an earlier implementation. These are **upstream source observations**, not proof of the exact stasel 153 binary's source configuration; a Claude scratch copy from WebRTC m150 is likewise not an exact-source receipt. Before proposing “enable HEVC in WebRTC,” enumerate `supportedCodecs()` and inspect the actual negotiated SDP, encoder implementation, VT hardware-use query, and receiver statistics on this package. A custom encoder factory or a different media path may be necessary.

A **post-change synthetic local loopback** in `work/continuation/codec-benchmark.log` now reports H.264 `640c34` (High level 5.2), `VideoToolbox`, **59.9 encoded/s and 59.9 sent/s** at 2940×1912, with **56.8 decoded/s** by a second peer on the same Mac. At 1920×1248 it reports 60 encoded/s and 61 decoded/s. This validates a substantial local encoder-path improvement over the 3–4 fps baseline, while leaving several gaps: the source is synthetic NV12, the decoder is the Mac rather than iPhone 17, the route is same-process loopback, p90 physical input-to-photon was not measured, and receiver `jitterBufferMs` reached a 261.9 ms median summary for the larger case. Reported QP 51 and ~0.8 Mb/s median on complex synthetic frames also do not establish readable code text. A physical phone capture and quality/latency comparison remains required before declaring engine parity.

**Immediate H.264 negotiation gate.** The level-3.1 offer is plainly incompatible with native 2940×1912 at 60 fps. Counting 16×16 macroblocks gives `ceil(2940/16) × ceil(1912/16) × 60 = 184 × 120 × 60 = 1,324,800` macroblocks/s. [Chromium's H.264 level limits](https://chromium.googlesource.com/chromium/src/+/787f41564/media/video/h264_level_limits.cc) list 983,040 for level 5.1 and 2,073,600 for level 5.2; thus **level 5.2 is the minimum nominal level for that size/rate**, subject also to profile, bitrate and actual device limits. Apple's [VT profile catalog](https://developer.apple.com/documentation/videotoolbox/kvtcompressionpropertykey_profilelevel) publishes H.264 High 5.2, but a constant's existence does not prove both devices accept the session. Let each peer advertise only a level/profile its runtime encoder/decoder can create and sustain; verify the final `profile-level-id` in *both* SDP directions and the emitted SPS, then require successful hardware frames and real receiver decode. [RFC 6184](https://www.rfc-editor.org/info/rfc6184/) allows asymmetric levels only when **both** sides say `level-asymmetry-allowed=1`; that flag does not magically upgrade a level-3.1 receiver. A receiver that advertises an older 4.1 ceiling must trigger a resolution/fps fallback, not an untruthful 5.2 bitstream. Practical candidate caps to test are 1920×1080 at 30 fps or 1280×720 at 60 fps for level 4.1; browser H.264 remains separately negotiated. If 5.2 fails on native devices, cap capture to the negotiated level before submission and retain a working H.264/VP8 fallback. Do not splice a higher SDP level without matching encoder, decoder and bitstream evidence.

## Prior art: what is useful and what is still unproven

| System | Published mechanism and useful lesson | Limitation for PocketDesk |
|---|---|---|
| Astropad LIQUID / Workbench | Astropad says LIQUID uses independent 64×64/128×128 dirty tiles, GPU work, UDP with “Velocity Control,” and switches to standard video coding for full-screen video. [Workbench 1.3 says](https://astropad.com/blog/workbench-1-3/) region-aware text/image coding and “30% faster overall.” [Workbench Vitals](https://support.astropad.com/en/articles/13978237-connection-requirements-quality) separately shows HEVC and Liquid tile bandwidth, supporting a real mixed-codec design. | Vendor descriptions omit reproducible encode/decode traces, device power and WAN conditions. “Perceptually lossless” is not bitwise lossless. The 30% baseline and metric are unspecified. Its claim that ordinary video always redraws a whole frame is too broad: inter-frame codecs exploit temporal/spatial redundancy. Tile independence trades compression efficiency for localized recovery. |
| Microsoft RDP | [Microsoft's graphics-encoding guidance](https://learn.microsoft.com/en-us/azure/virtual-desktop/graphics-encoding) describes content classification, adaptive graphics, delta detection/caching, AVC/HEVC and 4:2:0/4:4:4. It explicitly says mixed-mode is **software encoding only** in that Azure stack. | 4:4:4 and hardware video do not automatically combine there. AVC444/progressive/ClearCodec are useful design precedents, not a turnkey macOS/iOS component. Full-screen 4:4:4 increases bandwidth. |
| SPICE | [SPICE's own manual](https://www.spice-space.org/spice-user-manual.html) uses lossless image coding and heuristic lossy video regions; it warns that classifying updated text as video can lower quality. | Its compression/protocol implementation is old and not a direct Apple mobile solution; classification false positives matter. |
| Moonlight/Sunshine | [Moonlight's FAQ](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions) says Sunshine's variable frame rate follows content changes; low reported FPS on static screens is expected. Hardware video is effective for motion. | Game-stream design prioritizes full-frame motion. Static FPS counters alone are not a responsiveness metric. Its mobile decode and network route differ from PocketDesk. |
| Parsec BUD | [Parsec's compatibility guidance](https://support.parsec.app/hc/en-us/articles/32381568346644-Hardware-and-Software-Compatibility) ties its 4:4:4 HEVC option to specific NVIDIA/Intel hardware, with H.265 fallback rules. | BUD internals are proprietary. Parsec's published 4:4:4 support does **not** imply Apple M4→iPhone hardware 4:4:4 support. |
| Apple's High Performance Screen Sharing | [Apple says](https://support.apple.com/en-tm/guide/mac-help/mchl1883115d/mac) it offers 4:4:4, 30/60 fps and low latency on Apple-silicon **Mac-to-Mac** connections, with up to 75 Mb/s recommended for one 4K display. | It is not a public Mac-to-iPhone codec or proof of iPhone 4:4:4 hardware decode. Its bandwidth requirement also shows color fidelity has a cost. |
| Chrome Remote Desktop, NoMachine, Jump Fluid, VNC | These products demonstrate practical alternatives—screen-damage codecs, caching and hardware video—but public marketing is insufficient to assert the exact VP9 4:4:4 mode, Fluid 2 bitstream, or current mobile decode behavior. | Do not build around an unverified competitor implementation detail. Capture their output in a controlled comparison rather than infer internals. |

The standards contain more screen-specific tools than the currently configured path. [ITU-T H.265 SCC conformance](https://www.itu.int/epublications/publication/itu-t-h-265-1-2018-10-conformance-specification-for-itu-t-h-265-high-efficiency-video-coding) covers screen-extended profiles and palette/current-picture tools; [AOMedia's AV1 tool description](https://aomedia.org/docs/AV1_ToolDescription_v11-clean.pdf) describes palette and intra-block-copy modes. Those are **bitstream possibilities**, not evidence that Apple's selected hardware session, WebRTC package or phone decoder exposes them. The useful principle is content-aware screen coding; implementing SCC or AV1 from scratch is not a shortcut to it.

## Apple and browser capability gates

| Capability | Public evidence and required proof |
|---|---|
| Capture damage and pixels | [`dirtyRects`](https://developer.apple.com/documentation/screencapturekit/scstreamframeinfo/dirtyrects) is an array whose union covers redrawn and moved regions; combine with frame `contentRect`, scale and status from [Apple's capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos). It is a hint to validate against frame pixels, not a semantic text classifier. Capture output is IOSurface-backed, so a Metal diff/pack stage may avoid a full CPU readback; verify buffer format, synchronization and actual copies. [`captureResolution`](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration) and `sourceRect` need OS availability and live quality checks before use. |
| Low latency VideoToolbox | [Apple's conferencing sample](https://developer.apple.com/documentation/videotoolbox/encoding-video-for-low-latency-conferencing) creates a VT session with `kVTVideoEncoderSpecification_EnableLowLatencyRateControl` and sets `RealTime`. [Apple documents](https://developer.apple.com/documentation/videotoolbox/kvtvideoencoderspecification_enablelowlatencyratecontrol) no B-frame reordering/lookahead, an infinite GOP and temporal layers in that mode. Long GOP improves steady-state speed but loss recovery needs explicit IDR policy. Test supported properties, result codes, actual encoded profile and `UsingHardwareAcceleratedVideoEncoder`; do not equate setting a key with hardware use. |
| H.264/HEVC profiles and 4:4:4 | Apple's [public VT profile list](https://developer.apple.com/documentation/videotoolbox/kvtcompressionpropertykey_profilelevel) shows HEVC Main, Main10 and Main42210, **not a general HEVC Main 4:4:4 profile constant**. This is not a proof of impossibility, but there is no public end-to-end M4 encode → iPhone 17 hardware decode → WebRTC 4:4:4 contract here. Test `VTCopySupportedPropertyDictionaryForEncoder`, creation with requested pixel format/profile, actual bitstream SPS/VPS chroma format, phone VT decoder creation and [`UsingHardwareAcceleratedVideoDecoder`](https://developer.apple.com/documentation/videotoolbox/decompression-properties), then sustained heat/power. A source NV12 buffer has already discarded 4:4:4 chroma before encoding. Main10 is 10-bit **4:2:0**, not 4:4:4. |
| Per-region QP | Apple's [compression property catalog](https://developer.apple.com/documentation/videotoolbox/compression-properties) exposes frame QP hints and spatial adaptive QP, but no documented arbitrary ROI/QP map for the targeted VT encoder. Treat one-pass text ROI as unsupported until an exact public property and device test prove it. Raising whole-frame bitrate is available but costs bandwidth. |
| Lossless tile primitives | Apple documents [LZ4](https://developer.apple.com/documentation/compression/compression_lz4) as fast, lossless compression. It can encode small BGRA/RGB tiles, but must be profiled with real screenshots; photographic tiles may grow and should use video instead. Metal can do hashes/diffs/compose, but GPU-to-CPU readback and channel serialization may erase the gain. A raw 128×128 BGRA tile is 65,536 bytes before compression, so packetization and bounded memory matter. |
| Browser path | [RFC 7742's browser video floor](https://datatracker.ietf.org/doc/html/rfc7742) is VP8/H.264 Constrained Baseline; HEVC is optional and profile support varies. Keep H.264 negotiated fallback. A browser tile overlay would require a separate WebRTC data-channel decoder/compositor, likely WebGL/WebGPU/canvas work and actual Safari/Chrome tests; it does not come “free” with native Metal. |

## Three architecture choices

The figures below are **planning estimates, not measured latencies, bitrates or delivery commitments**. They assume one strong developer with AI coding help, a physically available phone and a testable direct local route. They exclude unpredictable App Review/relay rollout time. At 2940×1912, a raw BGRA frame is about 22.5 MB; at 60 fps it exceeds 10 Gb/s before protocol overhead. Thus neither full-frame raw nor independent lossless tiles under full-motion load are plausible WAN defaults. All designs need resolution/quality adaptation and a deterministic fallback.

| Option | Expected benefit and bandwidth pattern | Cost, failure modes and provisional effort |
|---|---|---|
| **A. Tuned hardware video over WebRTC**: verified low-latency H.264; HEVC only if a native sender/receiver path negotiates and decodes it. | Best fit for video/motion. Existing WebRTC ICE/TURN, congestion control, encryption and browsers remain useful. Indicative *budget* for a good local path: capture 5–17 ms, encode 3–12, packetize/transport 1–5, network 2–15, jitter/decode 5–25, display wait 0–17 = roughly 16–91 ms, excluding input dispatch/app rendering. Bitrate should be measured over static code, scrolling and video; expect near-zero on idle and multi-Mb/s on motion, not a single fixed number. | **~1–3 developer-weeks** for telemetry, VT proof and policy experiments; more if HEVC requires replacing the binary's encoder factory. NV12/4:2:0 may soften colored text. Higher resolution/bitrate increases encoder, radio and phone power. WebRTC adaptation and receiver buffer may still dominate. |
| **B. Hybrid hardware video + lossless dirty-tile UI layer**, tied to the same captured frame sequence. | Preserve crisp stationary text and thin colored edges while video handles motion. Sparse edits can cost tens of KB per update; 10% of a 2940×1912 BGRA frame is already ~2.25 MB **raw**, so compression and a strict coverage cutoff are mandatory. Proposed local overlay budget: damage/diff 1–4 ms, pack/compress 1–6, channel/network 2–15, phone decode/compose 1–5, display wait 0–17; video base can arrive earlier/later and must be synchronized. | **~4–8 developer-weeks** after A, plus device work. Requires pixel format/color matching, frame IDs, cache versioning, occlusion/resize invalidation, periodic resync, loss handling, expiry of stale tiles, bounded queues and a phone Metal compositor. [WebRTC data channels](https://www.w3.org/TR/webrtc/) default to reliable ordered delivery, which can stall newer tiles behind an old tile; use a separate bounded channel with appropriate ordering/retransmission or coalesced latest-state delivery, never the existing input/control channel. Dynamic areas need hysteresis or switch to video. CPU/GPU/radio and battery costs must be measured. |
| **C. Fully custom tile codec + UDP/QUIC transport** with independent tiles, mixed coding and custom adaptation. | Maximum control over damage, palette/text, partial recovery and prioritization; could excel on local sparse desktop scenes. Full-motion still needs hardware HEVC/H.264, as Astropad itself says. | **~12–24+ developer-weeks** for a robust native prototype and much more to equal mature NAT traversal, relay, congestion, security and browser support; uncertainty is high. Apple's [QUIC datagrams](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework) give best-effort messages, not fragmentation, receiver cache consistency or a TURN-equivalent service. Cellular packet loss, relay cost, handover, memory pressure and divergent native/browser implementations are major risks. The November target cannot responsibly depend on this. |

The latency rows are stage *budgets*: stages overlap, display waits vary by phase, and their sum is not a prediction. Input-to-photon additionally includes input transport, host event injection, app reaction and the next captured update. A 60 Hz display alone can add almost 17 ms wait. WAN/forced relay adds variable RTT and queueing, so local claims must never be projected onto cellular. Measure the selected ICE candidate pair and route; a nominal RTT is not input-to-visible delay. Compression may reduce bandwidth yet increase encode time, power, or stale buffering.

## Staged execution and falsification

**Gate 0 — instrument and repair the observed level fault (2–4 days estimated).** First verify level/profile at sender and receiver, plus successful encoded output at the proposed frame size/rate; the loopback receipt above already narrows a real test failure to the H.264 configuration/fallback path. Timestamp phone input send, Mac receive/inject, source display time and capture callback, frame enqueue/drop, encoder callback, RTP send, receiver arrival/decode/render callback and actual phone display/photodiode or high-frame-rate camera marker. Correlate with a monotonically increasing frame ID over the video, selected ICE pair, negotiated codec/profile, target/actual bitrate, encoded FPS, WebRTC `framesDropped`/jitter data and thermal state. Current `bench/stimulus.html` and `bench/analyze.py` are useful visual stimuli; distinguish distinct updates during a deliberately changing region from idle frame count. Record 5+ minute steady runs and cold/warm startup on the same resolution, zoom and network. If capture itself delivers ~20 distinct moving updates/s, an encoder replacement cannot produce 60 distinct updates.

**Gate A — launch candidate (1–3 weeks estimated).** On real M4/iPhone 17 and deployment OS, compare the present H.264 path with a positively identified hardware VT low-latency H.264 configuration. Try HEVC only behind capability negotiation and an H.264 fallback. Choose frame-rate-first versus quality-first policy by the physical task, not a synthetic encoder speed alone. Inspect text at source-scale and at PocketDesk's typical phone zoom; 4:2:0 colored glyph edges and capture downscale are different defects. Preserve browser H.264. If p95 input-to-photon or motion update cadence fails despite a fast encoder, fix the measured capture/transport/presentation stage rather than enter Gate B automatically.

**Gate B — constrained UI overlay, only on measured need (4–8 weeks estimated).** Start with a local, native-client lab build. For each complete capture, map Apple dirty rectangles into output pixels, pad for motion/antialiasing, classify using temporal activity and cheap color/edge statistics, compare hashes against the acknowledged receiver cache, compress selected BGRA tiles with LZ4/palette/raw, and send sequence + capture timestamp + dimensions + color-space metadata. Treat classifier output as uncertain; sample-check full-frame pixels and force periodic refresh. Overlay only after a matching base frame or an explicit cache epoch; discard late deltas and coalesce queue growth. Require 1–2 second recovery after injected tile loss, resize and reconnection. Stop sending tiles and fall back to video when damage coverage or encoded tile bytes exceed a measured threshold. For text, a simpler first experiment is a lossless high-resolution crop of a **user-selected zoom region** rather than a whole-screen classifier. Compare both against just raising H.264 bitrate/resolution.

**Gate C — post-launch only.** Build a custom codec/transport if A and B fail in repeatable tasks and profiling shows a quantified gain worth maintaining two media stacks. Proof requires direct local, congested Wi-Fi, LTE/5G, forced relay, packet loss and browser reachability, plus security/abuse review. A tile codec that is only faster on an uncongested local benchmark is not a commercial replacement for WebRTC.

Proposed **acceptance criteria**, subject to product owner approval: on `bench/stimulus.html` with continuous cursor/scroll/caret animation, at least **45 distinct updates/s median and ≥30 at p10** during a 60 Hz-capable local run; p90 inter-update gap **<50 ms**, down from the recorded 117 ms; p95 physical input-to-photon **<100 ms local** for a harmless click/typing task (explicitly a target, not an achieved result); no visibly persistent wrong tile after loss/resize; all code glyphs in a fixed source crop read correctly by a blind reviewer at the intended zoom; no sustained severe phone thermal state in a 20-minute session. Record p50/p95 separately for direct Wi-Fi, cellular and forced relay rather than using the local threshold as an away-from-home promise. Compare PocketDesk and Workbench side-by-side under the same router, display content, resolution, phone brightness and recording method, and use Workbench Vitals only as vendor-supplied corroboration. If Gate A meets task quality, defer B; if B adds more than ~10 ms p95, produces stale overlays, or costs disproportionate phone heat/data for no readable text gain, stop B.

## Contradictions and evidence limits

1. Astropad's LIQUID narrative contrasts tiles against video as though every changed pixel causes a full redraw; ordinary inter-frame video coding also uses predictions and can send small residuals. The meaningful difference is independent tile delivery and content selection, not the existence of change detection. Its <16 ms and 30% statements remain vendor claims with missing methods. [LIQUID](https://astropad.com/blog/liquid/), [Workbench 1.3](https://astropad.com/blog/workbench-1-3/).
2. Apple's Mac-to-Mac Screen Sharing advertises 4:4:4, while the public VideoToolbox profile list does not establish an iPhone-compatible 4:4:4 HEVC bitstream. Both can be true: Apple's private/proprietary stack and device constraints differ. Do not infer PocketDesk support from the first claim. [Screen Sharing](https://support.apple.com/en-tm/guide/mac-help/mchl1883115d/mac), [VT profiles](https://developer.apple.com/documentation/videotoolbox/kvtcompressionpropertykey_profilelevel).
3. Microsoft's RDP documents mixed content coding and 4:4:4, yet says its mixed-mode path is software only. “Hardware 4:4:4 content-aware RDP” should not be treated as one proven mode. [Microsoft](https://learn.microsoft.com/en-us/azure/virtual-desktop/graphics-encoding).
4. WebRTC upstream H.264 code sets real-time/no-reorder, but PocketDesk's specific stasel 153 binary has not been traced to that exact source revision. Its active VT mode, supported encoder list, HEVC interop and 4:4:4 path remain unverified. Test runtime state and actual bitstream before writing a platform promise. [Upstream source](https://webrtc.googlesource.com/src/+/27af5db5e08034ac8432bfa263edec29afe471cc/sdk/objc/Framework/Classes/VideoToolbox/RTCVideoEncoderH264.mm), [Apple VT sample](https://developer.apple.com/documentation/videotoolbox/encoding-video-for-low-latency-conferencing).

No new capture or VT micro-benchmark was run for this research document: ScreenCaptureKit would require verified Screen Recording permission for the probing process, and synthetic encoder/LZ4 timings would not isolate the observed physical-phone gap. The first useful experiment is the correlated end-to-end trace above, followed by a device capability probe and real-screen tile histogram. No current result supports the claim that a custom encoder would fix the observed lag.

## Final continuation check

Final 8-second Mac loopback windows negotiated H.264 `640c34` through VideoToolbox. At 2940×1912, median encoded/sent/decoded rates were 60/60/60 fps, encode 12.7 ms and decode 4.8 ms. At 1920×1248, encoded/sent were 60 fps and decoded 57 fps, encode 5.8 ms and decode 2.4 ms. These synthetic blocks are not text-fidelity or touch-to-display measurements. The machine also ran development checks during the overall run, so these are diagnostic receipts, not a controlled comparative benchmark.

A separate default-codec receiver check negotiated `640c1f`, scaled a 1920×1248 source to 720×468, and delivered about 59 fps without violating its level 3.1 macroblock budget. The production capture configuration also respects that negotiated budget before encoding. Browser capture bypasses this native resize policy to preserve fixed-pixel freshness markers.

The higher level is advertised only after a cached, bounded hardware decode probe accepts an inert High@5.2 4K frame. A successful frame establishes decoder format compatibility, not sustained 4K60 performance or thermal stability. Simulator and failed/timed-out probes retain default codec levels.
