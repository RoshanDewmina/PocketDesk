Rules for the whole pack:

- Every behaviour change has a kill switch: a host or phone `UserDefaults` key read through `StreamTuning` (so it appears in `summary`, the statistics JSONL and `experimentKeys`), and `PocketDeskLegacyStreamTuning` turns all of them off.
- Tests come first (TDD). Pure logic lives in `RemoteShared` or `RemoteHost/RemoteInputDriver.swift`, so it runs in `RemoteCoreTests` (macOS) and needs no simulator.
- No new files in Xcode targets unless unavoidable, because every new file means a regenerated `project.pbxproj` that other branches also touch. New logic goes into existing files, and new tests go into existing test classes' files. `bench/` (Python) is outside the project.
- Builds: `lockf /tmp/farside-perf-pack.lock /usr/bin/lockf -k /tmp/farside-xcodebuild.lock xcodebuild build-for-testing …`, then `xcrun xctest -XCTest <Class> <bundle>`. The outer pack lock means at most one of this pack's jobs waits on the shared lock at a time. DerivedData goes on the SSD (`/Volumes/Studio/Development/Caches/Xcode/DerivedData/FarsidePerfPack*`), with `-clonedSourcePackagesDirPath` reusing an existing WebRTC 153 checkout.
- No installs, no host restarts, no booted simulators (the iOS target is compile-checked with `-destination 'generic/platform=iOS Simulator'`).

## Item 1 — Merge pointer moves

### 1a. Phone: merge moves while the control channel is backed up

**Today.** Each `touchesMoved` produces one `.move` command. `NativeGestureEngine.sendMotion` → `PhoneRemoteModel.gesture(.move)` → `sendInput("move")` → `transmit` → `RemoteCoordinator.sendControl` → one JSON `ControlPacket` (≈ 170–215 B) on the single ordered, reliable `control` channel. Absolute placements (`moveTo`) come from direct touch, the iPad pointer and drag auto-pan.

- UIKit already delivers about one touch sample per frame, so a healthy link gains nothing from merging.
- During a Wi-Fi or AWDL stall, though, every sample queues in SCTP. Each later click waits behind all of them, and at 64 KB buffered `PeerMedia.sendControl` refuses, which **ends the session**.

**Design.** A pure struct, `PointerMoveCoalescer`, goes in `RemoteShared/ControlProtocol.swift`, next to `RemoteAction`. It is owned by `RemoteCoordinator`, which every phone message passes through.

- `offer(action, backlogged:, now:)` returns `.send([actions])` or `.held`.
  - A `move`/`moveTo` with no pending move and no backlog is sent at once (**pass-through, today's behaviour**).
  - While the channel is backlogged, moves merge into one pending slot:
    - relative `move` deltas sum;
    - `moveTo` keeps the newest point;
    - the newest `pointerSync.move` ordinal is kept. Host acknowledgement is cumulative (`applied` ≥ ordinal clears every earlier pending move in `PointerPredictor`), so the older ordinals are covered.
  - A move is mergeable only when everything except x/y/ordinal is equal: `action`, `epoch`, `modifiers`, the whole `interaction` envelope (token, hold, click count), and no `textFocusProbe`. Otherwise the pending move is sent first.
  - **Any other action** (click, key, scroll, text, release, pause, clipboard, heartbeat, …) flushes the pending move ahead of itself, so ordering never changes.
- **Backlogged** means `media.controlBufferedAmount ≥ 4 KB`, about 20 messages or about 170 ms of 120 Hz moves. It is not backlogged below that.
- A pending move is flushed when the backlog clears, or at the latest every 33 ms (one `Task` on the main actor). It is discarded on `stop`, `peerDisconnected`, `connectionLost` and session reset.
- **Drawn pointer.** The phone applies each local move to its predictor when it is offered, as today. The only difference is the host's single clamp of a merged delta versus the predictor's per-step clamp. That differs only if the merged moves hit a screen edge, and the next telemetry sample blends it out (45 ms). While backlogged, the Mac side is up to 33 ms behind, which is still far less than the backlog it replaces.
- Each move that merges into a pending one increments `counters.coalescedMove()`. This wires the "moves merged" overlay line (StreamStatistics.swift:610, :773), which always reads 0 today.
- A held move returns `true`. If the later flush is refused, the coordinator ends the session exactly as a refused immediate send does today.

**Kill switch.** Phone `PocketDeskMergePointerMoves` becomes `StreamTuning.mergePointerMoves` (tuned: true; legacy: false). Off means pass-through always, which is byte-for-byte today's traffic.

**Tests (RemoteCoreTests, `PointerMoveCoalescerTests` cases added to an existing test file):**

- pass-through when not backlogged;
- relative deltas sum under backlog, with the newest ordinal and a merged count;
- `moveTo` keeps the newest point;
- a different envelope, modifiers or epoch flushes first;
- a non-move action flushes the pending move first, in order;
- the flush when the backlog clears and the 33 ms deadline;
- `discard` on reset;
- the switch off sends everything immediately;
- non-move actions never merge.

### 1b. Host: main-queue input delay, measured (not moved)

**Built.**

- `RemoteCoordinator` stamps the arrival time (mach ms) of each control message in the data-channel callback, before the main-actor hop, and exposes it as `currentControlArrivalMs` while `onControl` runs.
- `RemoteHostModel.receive` records, for each user-input action:
  - `mainDelay = now − arrival`;
  - the `CGEvent` post duration (`handle` time).
- These go into `StreamCounters`, and from there into the host summary as `inputMainDelayP50Ms/P95Ms/MaxMs`, `inputPostP95Ms` and `inputEvents`. The phone overlay shows them on the input line.

**Deferred to after 3 Nov:** moving decode and admission off the main actor (an input actor), with latest-position-wins, and only if `inputMainDelayP95Ms` shows it matters on a loaded Mac.

**Tests:** counter percentiles and summary encoding; old phones decode a summary with the new fields; arrival stamping is nil outside `onControl`.

### 1c. Separate unordered pointer channel — evaluated, deferred past 3 Nov

It is not safe before 3 Nov, for three reasons found in the code (confirmed by the verifier on the integration branch, RemoteCoordinator.swift:669-679):

1. **Strict sequence.** Every control packet carries one session-wide `sequence`. The receiver rejects anything not strictly greater than the last one and **ends the session**. One reordered move on an unordered channel would disconnect the user. A second channel needs its own sequence space and replay window.
2. **Relative moves cannot be lossy.** `move` is a delta, and the phone's predictor replays unacknowledged deltas by ordinal. A lost delta silently shifts the Mac pointer from what the phone draws. The channel needs cumulative or absolute pointer state, and clicks must carry the absolute point. That is a protocol change on both ends plus a `SessionFeature` flag.
3. **Clicks can't overtake moves.** A click must land where the preceding moves put the pointer.

The integration branch's `file` channel shows the negotiation pattern to reuse: label, feature gate, and old phones closing unknown labels. It is recorded as the 1.1 item "unordered pointer channel" (report §8b #6).

## Item 2 — Newest frame wins (`encoderMaxInFlight`) on by default

**State.** `DesktopH264Encoder.encode` drops a frame at submit when `maxInFlight` frames are pending inside VideoToolbox, unless WebRTC asks for a key frame.

- `farside-efficiency-audit` (620f285), merged into the integration build .7 that this branch sits on, already defaults it on: `StreamTuning.tuned.encoderMaxInFlight = 1`.
- It also added the kill switches:
  - the runtime switch `NewestFrameWinsSwitch` (host Settings → "Newest frame wins", `PocketDeskNewestFrameWins`, read on every frame);
  - `PocketDeskEncoderMaxInFlight=0`.
- **This pack keeps that default and those switches, and fixes the stall risks the review found.**

**Findings (plan review plus verifier):**

1. **Silent drop holds the gate shut.** The `RTCVideoEncoderH264` output callback returns early, without calling WebRTC's callback, on a VideoToolbox error or `kVTEncodeInfo_FrameDropped` (upstream RTCVideoEncoderH264.mm:856-863).
   - That entry stays "in flight" until it ages out of `inFlightWindowMs` (250 ms). With a limit of 1, every frame submitted in that window is dropped: a visible freeze of up to 250 ms, most likely under contention.
   - **Fix:** a completed frame retires every *older* pending entry. VideoToolbox outputs in submit order, since the ObjC encoder turns frame reordering off (RTCVideoEncoderH264.mm:754). Those entries are counted as `encoderSilentDrops`.
   - The window drops to **100 ms** as the backstop for a drop with no later completion. That is still more than 3× the contended p90 of 28.6 ms and 2.5× the three-in-flight service time of 38 ms.
2. **Encode errors leave phantom entries.** `latency.submitted` runs before `inner.encode`, and its return value is ignored (DesktopH264Encoder.swift, integration :245-248). Several `RTCVideoEncoderH264` error paths return an error with no callback: an uninitialized session, a pool failure, `kVTInvalidSessionErr`.
   - **Fix:** remove the entry when the return is non-zero.
3. **Checks that pass.**
   - Key-frame requests are never dropped.
   - A restart frame is never dropped, because `latency.reset()` runs before the pending count.
   - A drop returns OK without a callback, the same path VideoToolbox's own drops take.

**Tests (RemoteCoreTests, `EncoderLatencyTrace` cases next to the existing encoder-trace tests):**

- a later completion retires older pending entries and reports them as silent drops;
- the pending count reopens at once after that;
- a never-completed entry stops counting after 100 ms and not before;
- `cancel(key:)` removes a failed submit;
- out-of-order keys are not miscounted (fallback path);
- the counter reaches the host summary.

**Kill switch:** unchanged. The Settings switch, `PocketDeskNewestFrameWins`, `PocketDeskEncoderMaxInFlight=0`.

**Measurement (no device):** a loopback A/B with `StreamLoopbackBenchmarkTests` (jump scene, 2560×1664), limit 0 vs 1, run through a new `POCKETDESK_BENCH_MAX_IN_FLIGHT` override. It records push→decoded p50/p90/p99 and drops. The Mac is shared, so the numbers are indicative only; the physical E7 run stays the release gate.

## Item 3 — Pacer headroom on LAN routes only

**Mechanism facts, corrected by the verifier.**

- The host source is a screencast (`videoSource(forScreenCast: true)`). For screenshare, libwebrtc applies `WebRTC-ProbingScreenshareBwe`, which is on by default with `1.0,2875,80,40,-60,3`: pacing factor **1.0**, a 2875 ms queue limit, and periodic ALR probing. Sources: alr_experiment.cc:51-56, video_send_stream_impl.cc:175-235, 494-522; the string is present in the M153 binary.
- Consequently **the `WebRTC-Video-Pacing` field trial is ignored for this stream.** That is why `factor:2.5` showed no gain (STREAM-FIX-REPORT §5). The `videoPacing` knob is dead for the desktop stream, and PERFORMANCE-PLAYBOOK §R8 is wrong on this point. The trial is also process-wide and read when the send stream is built, so it could never have been route-gated.
- The only per-route lever is the estimate ceiling, `setBweMinBitrateBps(maxBitrateBps:)` = encoder ceiling × headroom. It matters only once the estimate is pinned at the encoder ceiling. Its effect is limited to about **2×** in any case:
  - probes are capped at 2 × the allocated (encoder) maximum (probe_controller.cc:566-576);
  - AIMD growth is capped at 1.5 × acknowledged throughput (aimd_rate_control.cc:238).
- A loopback has no bottleneck, so it cannot show the estimate-collapse risk seen in earlier runs.

**Design.**

- `StreamTuning.lanBandwidthHeadroom`, from host defaults key `PocketDeskLANHeadroom`, range **1…2**, **default 1 (off)**.
- A pure `BandwidthCeilingPolicy.maxBitrateBps(ceiling:route:tuning:)` returns `ceiling × lanBandwidthHeadroom` only for `SeedRoute.lan`, which means a host↔host pair with RTT < 15 ms. Every other route, including unknown, gets `ceiling × bandwidthHeadroom` (1).
- `PeerMedia` uses it in all three places the ceiling is set:
  - `configureNativeSender`;
  - `seedBandwidthEstimate` (with the seed);
  - a new route-change step, which re-applies the ceiling with `currentBitrateBps: nil` when the classified route changes, including LAN→relay after an ICE restart.
- Relay and internet routes are never raised.

**Default stays 1** whatever the loopback shows. Roshan's physical A/B decides (PERF-PACK-PHONE-CHECKS §3).

**Tests (RemoteCoreTests, `QuickWinTuningTests`):**

- policy table: LAN ×2; p2p, relay, unknown ×1; a host pair at 40 ms RTT ×1;
- key parsing: 0, 3 or garbage give 1;
- `summary` shows "LAN headroom 2";
- the key is in `experimentKeys`;
- legacy gives 1;
- a route-change detector reports LAN→relay→LAN transitions exactly once each.

## Item 4 — Per-frame timing, camera kit, budgets

### 4a. Per-frame timing delivered to the phone (no bitstream change)

**Why not RTP extensions or SEI.**

- `abs-capture-time` and `video-timing` are compiled into M153, but the ObjC API exposes neither the receiver's per-frame capture time nor its timing info. `RTCRtpReceiver.sources` has no capture time.
- The wire RTP timestamp carries a random per-stream `StartTimestamp` (`RtpVideoSender::OnEncodedImage`), so host and phone RTP timestamps differ by an unknown constant.
- In-band SEI would work mechanically, and the verifier confirmed the placement rules. It changes the live bitstream, though, so it is **not for 3 Nov**.

**Design.**

1. **Host, per frame, no join needed.**
   - `PeerMedia.pushFrame` records `(pushMs, displayMs)`. `displayMs` is SCK's `displayTime` (RemoteCapture); it is 0 for the idle re-send of an unchanged frame.
   - `DesktopH264Encoder` keys that at `encode()` by the frame's exact (aligned) `timeStampNs`: the same key its latency trace already matches to `captureTimeMs`. No ±ms guessing.
   - On completion it has `(localRtp = image.timeStamp, bytes = image.buffer.count, displayMs, pushMs, encodedMs)`.
   - The host computes `frameHostP50Ms/P95Ms/MaxMs` (display → encoded, excluding re-sends) into `HostStreamSummary`, which is forwarded once a second as today.
2. **End-to-end join.**
   - The host also puts the last ≤ 64 records into the summary as compact integer arrays (`frameRecords`), within the 16 KB control limit.
   - The phone's `PocketDeskVideoDecoderFactory` returns a thin `TimedH264Decoder` wrapper around `RTCVideoDecoderH264`. It passes every call through and logs `(wireRtp = encodedImage.timeStamp, bytes = buffer.length, arrivalMs)` in a ring of 256. It also wraps the decode callback to log `decodedMs` by the frame's `timeStamp`, compared as `UInt32(bitPattern:)`.
   - A pure `FrameTimingJoin` finds `offset = wireRtp − localRtp`. Per candidate offset it counts records whose byte sizes match. It locks when one offset has ≥ 4 matches and at least twice the runner-up's votes. It re-locks after a reset (a new session or an encoder restart); both sides use 4-byte start codes and in-band SPS/PPS, so sizes are equal.
   - When locked, each host record joins to its phone record. With the phone's `ClockSyncEstimator` offset (±uncertainty), that gives `frameToPhoneMs` = Mac display → decoded on the phone.
3. **Per-second fields** (`StreamStatsReport`, JSONL, overlay line `frame host p50/p95 · to phone p50/p95 (n, ±clock)`; old peers ignore them):
   - host: `frameHostP50Ms`, `frameHostP95Ms`, `frameHostMaxMs`;
   - phone: `frameToPhoneP50Ms`, `frameToPhoneP95Ms`, `frameToPhoneMaxMs`, `frameTimedCount`, `frameJoinLocked`.
   - These are **data for Connection Health (D42)**; no Connection Health UI is built here.
   - Display → presented can be added later through the presentation tracker. SmoothMotion's presenter would need the join too, so that is out of scope.
4. **Kill switch.** Host `PocketDeskFrameTiming` becomes `StreamTuning.frameTiming` (tuned: true; legacy: false); off sends no records. The phone wrapper is pass-through, and its bookkeeping stops when no records arrive.

**Tests (RemoteCoreTests):**

- the join locks on the correct offset from sizes, rejects a runner-up that is too close, unlocks and re-locks after a new offset, and handles wraparound at 2³²;
- host record encoding stays under the size limit at 120 fps;
- percentiles exclude re-sends;
- **loopback proof:** two in-process `PeerMedia` (the existing loopback pattern) stream synthetic frames with `frameTiming` on:
  - the host summary carries records;
  - the decoder wrapper sees every frame;
  - the join locks;
  - `frameToPhone` is finite and non-negative for ≥ 80 % of frames;
  - the decoded frame count equals the count with the switch off.

### 4b. 240 fps camera glass-to-glass kit

- **Stimulus.** Farside Test Pad `--bench` already draws a large ms clock, the marker strip and a flash target (FarsideTestPad/BenchPad.swift, BenchState.swift). Add an **auto-flash** mode to `BenchState`, a pure and testable struct:
  - the full-width flash band toggles black↔white at a jittered interval of 400–700 ms, seeded;
  - the irregular spacing makes the pairing of Mac and phone transitions unambiguous, because intervals are far longer than any plausible latency;
  - key `a`, command `bench.autoflash on|off`;
  - each shown toggle is logged with its mach ms (`bench.flashShown`), as the manual flash already is.
- **Analysis.** `bench/glass_to_glass.py` (procedure in `bench/CAMERA-KIT.md`), using Python 3 and ffmpeg/ffprobe, with no OpenCV:
  - takes two ROIs, Mac panel and phone panel, as `x,y,w,h` fractions, or finds them automatically as the two regions of largest luma variance;
  - extracts per-frame mean luma with ffmpeg `crop,signalstats`;
  - takes real frame times from ffprobe (240 fps; a VFR or slow-motion edit list is handled by using `best_effort_timestamp_time` and checking the median interval ≈ 4.17 ms);
  - detects transitions with hysteresis at the midpoint between the ROI's dark and bright levels, interpolated to sub-frame time;
  - pairs each Mac transition with the next phone transition of the same polarity inside a 400 ms window;
  - reports n, p50/p95/p99/max and the ±½-frame (±2.1 ms) quantisation;
  - `--touch-frames touches.csv` computes touch-to-photon from hand-marked finger-contact frames;
  - it prints and writes JSON.
- Verifier notes adopted:
  - `--fps N` rescales a slow-motion export whose timestamps are stretched;
  - both targets go at the same scan-out height;
  - `--window-ms` is raised for stall runs.
- **Tests.** `bench/tests/test_glass_to_glass.py` generates synthetic 240 fps clips with ffmpeg `lavfi` at known delays (e.g. 37.5 ms and 52.1 ms, with jitter) and asserts the recovered p50 within ±2.5 ms. This can run on `roshan-pc-1` (ssh pc), since it needs no Mac.
- **Instructions.** `bench/CAMERA-KIT.md`: camera placement, 240 fps slow-motion on a *second* device (the iPhone under test can't film itself), brightness, runs (LAN, forced relay, cellular, 5 Mb/s cap, 1–2 % loss) and how to export the original file.

### 4c. Replacement latency budgets (proposal; decision D44 in PRODUCT §16, text in §9)

These replace "input-to-visible p95 ≤ 150 ms LAN / 400 ms relay" (PRODUCT.md:545). They are proposed targets, to be confirmed by the camera baseline before any listing claim.

| Condition | Glass-to-glass (camera) | Touch-to-photon | Reference |
|---|---|---|---|
| LAN, same Wi-Fi, 60 fps | p50 ≤ 35 ms, p95 ≤ 50 ms | p50 ≤ 60 ms, p95 ≤ 90 ms | Measured: Sidecar 10–20 ms; Steam ≈ 20 ms; Moonlight with a PC host ≈ 20 ms; Moonlight/Apollo +17 ms wired, +25 ms iPad Wi-Fi; GFN 17 ms click-to-photon at NVIDIA's venue. **Floor risk: Sunshine on a Mac host measured 80 ms.** The 35/50 figures are the competition report's proposal, not a Moonlight measurement |
| Congested Wi-Fi | p95 ≤ 120 ms, no resolution change | — | GFN 117–125 ms on 5 GHz laptop |
| Relay, 40 ms RTT | p95 ≤ RTT + 70 ms (≈ 110 ms) | p95 ≤ RTT + 100 ms | Moonlight "~25 ms across the country" |
| Relay or cellular, 100 ms RTT | p95 ≤ 200 ms, ≥ 30 fps | p95 ≤ 250 ms | GFN < 80 ms gate |
| 5 Mb/s cap | p95 ≤ 200 ms, sender queue ≤ 100 ms | — | Stadia 543 ms (the failure mode) |

Today's uncalibrated figures are 56–85 ms p50 and 84–111 ms p95 glass-to-glass, and 109–130 ms touch-to-photon. That means LAN misses the new bar; this is honest, and it is the purpose of items 1–3.

## Delegation, order and risks

1. **Base.** Rebased onto `integration-2026-09-30` (build .7) before any Swift work. `pocketdesk-remote-chat` fast-forwards to it; rebase again if integration moves.
2. **Order.** Camera kit (done first, independent) → item 2 → item 3 → item 1a/1b → item 4a (delegated to one Opus task agent in its own worktree, sharing the pack build lock).
3. **Risks and mitigations.**
   - Merged moves: pass-through unless backlogged, plus the switch.
   - Silent-drop retirement: in-order output assumption, backed by the fallback window.
   - LAN headroom: shipped off.
   - Frame-timing records: bounded size, pure bookkeeping, failure means no data.
