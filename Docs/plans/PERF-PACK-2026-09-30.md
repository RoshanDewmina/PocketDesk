Branch `farside-perf-pack`, created from `pocketdesk-remote-chat` at a567310 (build .6). It will be rebased onto `pocketdesk-remote-chat` once `integration-2026-09-30` (build .7: connection-health, efficiency, smooth-motion, polish, transfer) fast-forwards it. Every line reference below is to a567310 unless it says "integration".

Scope: competition report §8a items 3, 4, 5, 6 and 7 (`~/reports/src/farside-competitors-2026-09-30/FARSIDE-COMPETITION-REPORT-2026-09-30.md`). Evidence: `research/MOONLIGHT-CLIENT-DEEP-DIVE.md` (R1, rows 12–13), `research/SUNSHINE-HOST-DEEP-DIVE.md` (§1(d), §5 input table), `research/CLOUD-GAMING-BENCHMARKS.md`, and in-repo `Docs/research/2026-09-28-round2/PERFORMANCE-PLAYBOOK.md` (R7, R8, §7) and `STREAM-FIX-REPORT.md` §5–6.

Rules for the whole pack:

- Every behaviour change has a kill switch: a host or phone `UserDefaults` key read through `StreamTuning` (so it appears in `summary`, the statistics JSONL and `experimentKeys`), and `PocketDeskLegacyStreamTuning` turns all of them off.
- Tests come first (TDD). Pure logic lives in `RemoteShared` or `RemoteHost/RemoteInputDriver.swift`, so it runs in `RemoteCoreTests` (macOS) and needs no simulator.
- No new files in Xcode targets unless unavoidable, because every new file means a regenerated `project.pbxproj` that other branches also touch. New logic goes into existing files, and new tests go into existing test classes' files. `bench/` (Python) is outside the project.
- Builds: `lockf /tmp/farside-perf-pack.lock /usr/bin/lockf -k /tmp/farside-xcodebuild.lock xcodebuild build-for-testing …`, then `xcrun xctest -XCTest <Class> <bundle>`. The outer pack lock means at most one of this pack's jobs waits on the shared lock at a time. DerivedData goes on the SSD (`/Volumes/Studio/Development/Caches/Xcode/DerivedData/FarsidePerfPack*`), with `-clonedSourcePackagesDirPath` reusing an existing WebRTC 153 checkout.
- No installs, no host restarts, no booted simulators (the iOS target is compile-checked with `-destination 'generic/platform=iOS Simulator'`).

## Item 1 — Merge pointer moves

### 1a. Phone: one move message per send tick

**Today.** Each `touchesMoved` produces one `.move` command. `NativeGestureEngine.sendMotion` (NativeGestureEngine.swift:407-429) → `PhoneRemoteModel.gesture(.move)` (RemotePhoneApp.swift:739-748) → `sendInput("move")` → one JSON `ControlPacket` (≈170–215 B) on the single ordered, reliable `control` channel. Absolute placements (`pointTo` → `moveTo`, RemotePhoneApp.swift:717-729) come from direct touch, the iPad pointer (`HardwarePointerRouter`) and drag auto-pan (a 16 ms loop in NativeSessionView.swift). UIKit already delivers touches once per frame, so on a healthy link the message rate is about the display rate. The win is when several sources fire in one tick (auto-pan plus finger, hover plus drag) and, above all, when the channel is backed up (Wi-Fi stall or AWDL): today every move queues in SCTP behind the stall, and each later click waits behind all of them.

**Design (Moonlight's accumulator, InputStream.c:707-771).** A new pure struct, `PointerMoveCoalescer`, goes in `RemoteShared/NativeGestureEngine.swift` next to `NativeGestureCommand`:

- `offer(.relative(delta) | .absolute(point, modifiers), epoch:, now:, backlogged:) -> Decision` returns `.send(PendingMove)` or `.hold(flushAt:)`.
- **Leading edge.** If no move went out in the last `minInterval`, the move is sent at once, so a lone move gets no added delay. Otherwise it merges into the pending slot:
  - relative deltas sum;
  - an absolute point replaces the pending one;
  - a change of kind, modifiers or epoch first sends the pending move, then starts a new slot.
- `minInterval` is 1/120 s. It is 1/30 s while `backlogged`, meaning the control channel's `bufferedAmount` is at least 8 KB, about 40 messages.
- `takePending()` returns the pending move. Before **every** other `sendInput` action (click, drag, scroll, key, text, release) the phone calls it and sends the move first, so the order of moves relative to other input never changes. A trailing flush runs at `flushAt` through one `DispatchQueue.main.asyncAfter`, cancelled when the slot empties.
- `discard()` clears the slot. It runs on `cancelInput`, `release`, a geometry-epoch change and disconnect: a held delta from an old geometry must never be sent.
- Each move that merges into a pending one calls `counters.coalescedMove()`. This fixes the "moves merged" line (StreamStatistics.swift:610, :773), which reads 0 today because nothing calls it.

**Pointer overlay.** One `PointerSync` ordinal is reserved per **message**, when it is sent. `pointerOverlay.localMove/localWarp` is applied at send time with the **merged** delta, so the predictor's per-step clamp replays exactly the single clamp the host applies. The drawn pointer is therefore at most one tick (≤ 8.3 ms) behind the finger while a move is held, and never while moves are sparse. This is the "merging belongs with the ordinal owner" condition that STREAM-FIX-REPORT §5 recorded when an earlier attempt was removed.

**Return value.** `gesture(.move)` returns true for a held move, because it will be sent unless the channel refuses it, and the engine's `pointerMotionActive` expects that. If the later send is refused, the move is dropped and counted, exactly as a refused immediate send is today.

**Kill switch.** Phone `PocketDeskMergePointerMoves` becomes `StreamTuning.mergePointerMoves` (tuned: true, legacy: false). Off sends immediately, which is today's behaviour.

**Tests (RemoteCoreTests, new cases in `RemoteTests/NativeInteractionTests.swift` or the nearest existing gesture test file):**

- a lone move is sent immediately;
- three moves in one tick produce one send with the summed delta and a merged count of 2;
- a trailing flush fires at `flushAt`;
- an absolute move replaces the previous absolute one;
- relative then absolute sends the relative move first;
- a modifier change splits the slot;
- a change of epoch splits the slot, and the old delta is dropped when `discard()` runs;
- the backlogged interval is 1/30 s;
- non-finite deltas are ignored;
- the switch off means every offer is `.send`.

A phone-side ordering check goes into the existing `RemotePhoneTests` input-probe tests: a click right after a held move records the move first. It is compile-only here, because no simulator is booted.

### 1b. Host: inject off the main queue, latest position wins

**Today.** `RemoteCoordinator.peer.onControl` decodes each packet on the main actor (RemoteCoordinator.swift:616-633). `RemoteHostModel.receive` (HostModel.swift:1394-1539) then admits it: epoch, freshness, lease, Accessibility, E2E fence. It calls `RemoteInputDriver.handle`, which builds and posts the `CGEvent` synchronously on main. The playbook measured posting as cheap **[M]**, but it is a WindowServer round trip on a loaded Mac, and every move pays it on the thread that also runs SwiftUI and timers.

**Design (smallest change that takes the frequent path off main).** All admission state stays on main; only the posting changes. A new `RemoteInputEventSink.queued(base:)` in RemoteInputDriver.swift wraps the live sink:

- It owns a serial `DispatchQueue(label: "farside.input", qos: .userInteractive)`.
- **Plain moves and drags go async.** `mouseSequence([one .mouseMoved or .leftMouseDragged event])` is appended to a lock-protected FIFO, and a drain is scheduled on the queue if none is pending. The call returns `true`. `CGEvent(mouseEventSource:…)` creation is effectively infallible and was already treated that way.
- **The drain merges consecutive pending `.mouseMoved` events** with the same flags and keeps only the last: latest position wins, as in Sunshine (input.cpp:1816-1826). `.leftMouseDragged` events are **not** merged, because a drag path matters in drawing and selection apps. Each dropped move increments a merged counter that the host summary reports as `hostMovesMerged`.
- **Everything else is synchronous on the queue:** clicks, button downs and ups, `release()`, scroll, text and keys go through `queue.sync { drainPending(); post }`. Ordering against queued moves is therefore guaranteed. Every mouse-up, including the release in termination and `endCapture`, has been posted before `handle` or `release()` returns, so a quitting host can never leave a button held.
- `pointerLocation` stays synchronous and unchanged.

`RemoteInputDriver` keeps every decision it makes today: the pointer chain, clamping, `lastPoint`, the click sequence, holds and scroll streams. The pointer-chain logic already treats "cursor reads as a point this driver recently posted" as lag. A merged-away point is simply never observed, so it cannot match and cannot mislead.

Moving decode and admission themselves off main (an input actor) is a bigger change across the coordinator and HostModel state. It is **documented for after 3 Nov**, not built.

**Kill switch.** Host `PocketDeskInputQueue` becomes `StreamTuning.inputQueue` (tuned: true, legacy: false). Off means `HostModel` constructs `RemoteInputDriver()` with `.live` exactly as today. The switch is read once per host process: `HostModel` creates the driver once.

**Tests (RemoteCoreTests, `RemoteTests/RemoteInputDriverTests.swift` or the existing input-driver test file).** They use a recording base sink that never posts real events:

- a burst of moves while the queue is blocked (a semaphore in the base sink) drains as the last move only, and reports the merged count;
- drags are never merged;
- a click after queued moves posts the moves (merged) and then the click, in order;
- `release()` posts its mouse-up before returning;
- a mixed sequence keeps its relative order;
- off switch → `.live`-equivalent synchronous behaviour;
- `handle` returns `accepted` for queued moves.

No test posts a real `CGEvent`.

### 1c. Separate unordered pointer channel — evaluated, deferred past 3 Nov

It is not safe before 3 Nov, for three reasons found in the code:

1. **Strict sequence.** Every control packet carries one session-wide `sequence`. The receiver rejects anything not strictly greater than the last one and **ends the session** (RemoteCoordinator.swift:619-631). One reordered move on an unordered channel would disconnect the user. A second channel needs its own sequence space and replay window.
2. **Relative moves cannot be lossy.** `move` is a delta applied to the cursor, and the phone's predictor replays unacknowledged deltas by ordinal (PointerPrediction.swift). With `maxRetransmits = 0`, a lost delta silently shifts the Mac pointer from what the phone draws. The channel needs cumulative or absolute pointer state, and clicks must carry the absolute point. That is a protocol change on both ends plus a `SessionFeature` flag for old peers.
3. **Clicks can't overtake moves.** A click must land where the preceding moves put the pointer. That needs the click-carries-position rule from point 2 and host logic that drops only moves older than the click.

The integration branch's `file` channel (PeerMedia, integration) shows the negotiation pattern to reuse later: label, feature gate, old phones closing unknown labels. Recorded in the plan as the 1.1 item "unordered pointer channel" (report §8b #6). Items 1a and 1b already remove most of the head-of-line cost, because a stall now queues about one merged move per 33 ms instead of every touch sample.

## Item 2 — Newest frame wins (`encoderMaxInFlight`) on by default

**State.** `DesktopH264Encoder.encode` (DesktopH264Encoder.swift:202-231) drops a frame at submit when `maxInFlight` frames are pending inside VideoToolbox, unless WebRTC requests a key frame. It defaults to nil (off). `farside-efficiency-audit` 620f285, now merged into `integration-2026-09-30` (546e293), already sets `StreamTuning.tuned.encoderMaxInFlight = 1`. It also adds the runtime kill switch `NewestFrameWinsSwitch` (host Settings → "Newest frame wins", defaults key `PocketDeskNewestFrameWins`, read on every frame) and `liveSummary` in statistics. `PocketDeskEncoderMaxInFlight=0` also turns it off. **This pack does not re-implement the default**; that would only create merge conflicts. It verifies the mechanism and fixes what the review below finds.

**Verification findings (code review):**

- Key-frame requests are never dropped (`requestsKeyFrame`). A restart frame is never dropped either: `latency.reset()` runs before the pending count is read. Both are correct.
- **Risk: a frame that VideoToolbox drops silently holds the gate shut for up to `inFlightWindowMs` = 250 ms.** `RTCVideoEncoderH264`'s output callback returns without calling WebRTC's callback on a VT error or `kVTEncodeInfo_FrameDropped`. That pending entry then counts as in flight until it ages out of the 250 ms window. With a limit of 1, every frame submitted in that window is dropped, which is a visible freeze of up to 250 ms. Silent VT drops are most likely exactly when the encoder is contended, which is when this feature is active. **Fix:** shorten the window to 100 ms. That is still more than 3× the measured contended p90 (28.6 ms) and 2.5× the three-in-flight service time (38 ms, EFFICIENCY-AUDIT). Also count `inFlightExpired`, the entries that aged out without a callback, in the encoder trace, so a silent drop is visible in statistics.
- A dropped frame returns `WEBRTC_VIDEO_CODEC_OK` without a callback. libwebrtc's `FrameEncodeMetadataWriter` keeps that frame's timing entry until it is superseded, so nothing leaks, and the same path is used for VT's own drops today.

**Tests (RemoteCoreTests; new cases next to the existing encoder-trace tests):**

- `EncoderLatencyTrace.pending(withinMs:)` releases a never-completed entry after 100 ms and not before;
- with limit 1, a silent drop blocks at most 100 ms of submits;
- a key-frame request is never dropped;
- the expired counter increments once per silently dropped frame.

**Kill switch:** unchanged from the integration branch. Settings switch, `PocketDeskNewestFrameWins`, `PocketDeskEncoderMaxInFlight=0`.

**Measurement (no device):** a loopback A/B with `StreamLoopbackBenchmarkTests` (jump scene, 2560×1664), `POCKETDESK_ENCODER_MAX_IN_FLIGHT` 0 vs 1. It needs a small environment override added to the benchmark. The run records push→decoded p50/p90/p99 and dropped-at-submit. The Mac is shared, so the numbers are indicative only, and the physical E7 run stays the release gate.

## Item 3 — Pacer headroom on LAN routes only

**Mechanism facts.**

- libwebrtc paces at `pacing_factor` (1.1) × the loss-based target estimate. The estimate is capped by `setBweMinBitrateBps(maxBitrateBps:)`, which today is `ceiling × bandwidthHeadroom`, with headroom 1 on every route (PeerMedia.swift:443-446, :519-527). A 400 KB IDR at 1.1 × 25 Mb/s takes about 115 ms to leave the pacer.
- **The `WebRTC-Video-Pacing` field trial is process-wide and fixed before the first `RTCPeerConnectionFactory` exists** (`StreamTuning.prepareRuntime`, StreamTuning.swift:222-232). The route is only known after ICE, so the trial **cannot be route-gated**. Setting it would also change relay and internet routes, which the brief forbids. It is not used; this is documented.
- Prior evidence (STREAM-FIX-REPORT §5): 2× headroom cut the page-jump p90 from 130 to 60 ms in the first runs. Across 4 repeated connections, though, the estimate stayed near the 10 Mb/s seed in 3 and collapsed once. Those runs predate the current seed policy (second sample plus one re-seed), which later gave 0 collapses in 42 connections. `factor:2.5` alone showed no gain. The effect is therefore **unproven** and needs an A/B.

**Design.** Route-gated headroom:

- `StreamTuning.lanBandwidthHeadroom: Int`, read from host defaults key `PocketDeskLANHeadroom`, range 1…4.
- A pure `BandwidthCeilingPolicy.maxBitrateBps(ceiling:route:tuning:)` returns `ceiling × lanBandwidthHeadroom` only for `SeedRoute.lan`, which means a host↔host pair with RTT < 15 ms (existing `SeedRoute.classify`). It returns `ceiling × bandwidthHeadroom` (1) for p2p, relay and unknown.
- `PeerMedia` applies it:
  - in `configureNativeSender` (with the last classified route);
  - on every statistics sample whose route class changed, including LAN→relay after an ICE restart, which goes back down.
- It is only ever raised on LAN, the relay path is untouched, and nothing changes when the route is unknown.

The estimate still only grows where probing proves capacity. Screen-share content turns on periodic ALR probing, and the pacer drains faster only if the link actually carries it.

**Default.** `lanBandwidthHeadroom = 3` **only if** the loopback A/B shows (a) lower jump-scene pacer delay / p90 and (b) no estimate collapse in ≥ 6 connections per arm. **Otherwise ship it at 1 (off)** with the switch, and leave the physical A/B for Roshan. This is the conservative fallback.

**Tests (RemoteCoreTests, `QuickWinTuningTests`):**

- policy table: LAN ×3; p2p, relay and unknown ×1; a LAN pair with RTT 40 ms (tunnel) gives ×1;
- defaults key parsing: 0 or out of range gives 1;
- `summary` shows "LAN headroom 3";
- the key is in `experimentKeys`;
- legacy gives 1;
- relay → LAN → relay transitions return to ×1 (pure policy plus a route-change detector struct).

**Measurement:** a loopback A/B (the loopback route classifies as `lan`), `POCKETDESK_BENCH_LAN_HEADROOM` 1 vs 3, jump scene, 6 connections per arm. The run records `pacerDelayMs`, the estimate, and p50/p90/p99.

## Item 4 — Per-frame timing, camera kit, budgets

### 4a. Per-frame host timing delivered to the phone

**Why not RTP extensions.** `abs-capture-time` and `video-timing` are compiled into M153 (playbook §7). The ObjC API, however, exposes neither the receiver's per-frame capture time nor `getSynchronizationSources`. The only header-extension API is negotiation (`RTCRtpTransceiver.setHeaderExtensionsToNegotiate`). Matching data-channel records by RTP timestamp does not work either: the wire RTP timestamp adds a random per-stream `StartTimestamp` that neither side can read (`RtpVideoSender::OnEncodedImage`).

**Design: in-band H.264 SEI (user data unregistered, payload type 5), written by our own encoder wrapper and read by our own decoder wrapper.**

- **Host.**
  - `PeerMedia.pushFrame` also records `(pushMs, displayMs)` in a small ring. `displayMs` is SCK's `SCStreamFrameInfo.displayTime`, already read in RemoteCapture.swift:787; it is 0 for an idle re-send, where the display time is older than 100 ms.
  - In `DesktopH264Encoder`'s wrapped callback, the ring entry is matched by `image.captureTimeMs`. The match uses the nearest entry within ±2 ms, because `ObjCVideoTrackSource`'s timestamp aligner may shift it slightly.
  - The wrapper then inserts one SEI NAL **immediately before the first VCL NAL** (type 1 or 5), after any SPS/PPS. It must never go between SPS and PPS: `RTCVideoDecoderH264`'s format-description reader expects the PPS right after the SPS.
  - Payload: 16-byte UUID, then version 1, `displayMs`, `pushMs` and `encodedMs` (host mach ms as `UInt64` µs). About 45 bytes per frame, roughly 22 kb/s at 60 fps. Emulation-prevention bytes are inserted.
  - Browser peers use the compatible factory and are unaffected.
- **Phone.**
  - A new `FrameTimingDecoder` wrapper around `RTCVideoDecoderH264` (in `VideoCodecPolicy.swift`, returned by `PocketDeskVideoDecoderFactory`) scans the Annex B buffer up to the first VCL NAL.
  - It parses the SEI and records `wireRtpTimestamp → HostFrameTiming` in a lock-protected ring of 64 entries.
  - It does **not** change the bitstream; VideoToolbox ignores unregistered SEI.
  - `FrameObserver.renderFrame` looks up `frame.timeStamp` (the RTP timestamp, which `RTCVideoFrame` exposes) and hands the timing to the counters. It is forwarded with the frame like the bench marker, so the presentation tracker can join it where the drawable reports `presentedTime`.
- **Clock.** Phone ↔ host offset comes from the existing Cristian `ClockSyncEstimator`, with its uncertainty reported.
- **Per-second fields** (`StreamStatsReport`, JSONL, overlay; old peers ignore them; each is a p50/p95/max over that second's frames):
  - `frameHostMs`: display → encoded, host only, no clock needed;
  - `frameToPhoneMs`: display → decoded frame arriving at the phone renderer;
  - `frameAgeMs`: display → presented, where the presentation join works, else absent;
  - `frameTimedCount`.
  - These are **data for Connection Health (D42)**; this pack builds no Connection Health UI. The only visible change is one line in the existing Stream statistics overlay.
- **Kill switch.** Host `PocketDeskFrameTimingSEI` becomes `StreamTuning.frameTimingSEI` (tuned: true only after the loopback proof below passes, else false; legacy: false). The phone parser is passive and always on; it costs a scan of the first few NAL headers.

**Tests (RemoteCoreTests):**

- SEI writer/reader round trip, including values that produce `00 00 0x` byte runs, which exercises emulation prevention;
- insertion lands after SPS/PPS and before the first IDR slice, never between SPS and PPS;
- a buffer with no VCL NAL is left unchanged;
- a malformed or truncated SEI is ignored and does not crash;
- ring matching within ±2 ms;
- an idle re-send gets `displayMs` 0 and is excluded from the percentiles;
- **loopback proof:** two in-process `PeerMedia` (the existing loopback test pattern, not the opt-in benchmark) stream 60 synthetic frames with SEI on:
  - every decoded frame decodes, same count as with SEI off;
  - ≥ 90 % of frames carry a timing record;
  - `frameToPhoneMs` is finite and positive;
  - key frames still decode.

### 4b. 240 fps camera glass-to-glass kit

- **Stimulus.** Farside Test Pad `--bench` already draws a large ms clock, the marker strip and a flash target (FarsideTestPad/BenchPad.swift, BenchState.swift). Add an **auto-flash** mode to `BenchState`, a pure and testable struct:
  - the full-width flash band toggles black↔white at a jittered interval of 400–700 ms, seeded;
  - the irregular spacing makes the pairing of Mac and phone transitions unambiguous, because intervals are far longer than any plausible latency;
  - key `a`, command `bench.autoflash on|off`;
  - each shown toggle is logged with its mach ms (`bench.flashShown`), as the manual flash already is.
- **Analysis.** `bench/camera/glass_to_glass.py`, using Python 3 and ffmpeg/ffprobe, with no OpenCV:
  - takes two ROIs, Mac panel and phone panel, as `x,y,w,h` fractions, or finds them automatically as the two regions of largest luma variance;
  - extracts per-frame mean luma with ffmpeg `crop,signalstats`;
  - takes real frame times from ffprobe (240 fps; a VFR or slow-motion edit list is handled by using `best_effort_timestamp_time` and checking the median interval ≈ 4.17 ms);
  - detects transitions with hysteresis at the midpoint between the ROI's dark and bright levels, interpolated to sub-frame time;
  - pairs each Mac transition with the next phone transition of the same polarity inside a 400 ms window;
  - reports n, p50/p95/p99/max and the ±½-frame (±2.1 ms) quantisation;
  - `--touch-frames touches.csv` computes touch-to-photon from hand-marked finger-contact frames;
  - it prints and writes JSON.
- **Tests.** `bench/tests/test_glass_to_glass.py` generates synthetic 240 fps clips with ffmpeg `lavfi` at known delays (e.g. 37.5 ms and 52.1 ms, with jitter) and asserts the recovered p50 within ±2.5 ms. This can run on `roshan-pc-1` (ssh pc), since it needs no Mac.
- **Instructions.** `bench/camera/README.md`: camera placement, 240 fps slow-motion on a *second* device (the iPhone under test can't film itself), brightness, runs (LAN, forced relay, cellular, 5 Mb/s cap, 1–2 % loss) and how to export the original file.

### 4c. Replacement latency budgets (proposal; decision D44 in PRODUCT §16, text in §9)

These replace "input-to-visible p95 ≤ 150 ms LAN / 400 ms relay" (PRODUCT.md:545). They are proposed targets, to be confirmed by the camera baseline before any listing claim.

| Condition | Glass-to-glass (camera) | Touch-to-photon | Reference |
|---|---|---|---|
| LAN, same Wi-Fi, 60 fps | p50 ≤ 35 ms, p95 ≤ 50 ms | p50 ≤ 60 ms, p95 ≤ 90 ms | Sidecar 10–20 ms; Steam ≈ 20 ms; Moonlight LAN ≤ 35 / ≤ 50 ms; GFN 17 ms touch at venue |
| Congested Wi-Fi | p95 ≤ 120 ms, no resolution change | — | GFN 117–125 ms on 5 GHz laptop |
| Relay, 40 ms RTT | p95 ≤ RTT + 70 ms (≈ 110 ms) | p95 ≤ RTT + 100 ms | Moonlight "~25 ms across the country" |
| Relay or cellular, 100 ms RTT | p95 ≤ 200 ms, ≥ 30 fps | p95 ≤ 250 ms | GFN < 80 ms gate |
| 5 Mb/s cap | p95 ≤ 200 ms, sender queue ≤ 100 ms | — | Stadia 543 ms (the failure mode) |

Today's uncalibrated figures are 56–85 ms p50 and 84–111 ms p95 glass-to-glass, and 109–130 ms touch-to-photon. That means LAN misses the new bar; this is honest, and it is the purpose of items 1–3.

## Delegation, order and risks

1. Rebase onto the integrated `pocketdesk-remote-chat` before touching `RemoteInputDriver`, `RemotePhoneApp`, `PeerMedia`, `DesktopH264Encoder`, `StreamTuning` or `VideoPresentationProbe`.
2. Order: Item 2 fix (small) → Item 3 → Item 1 → Item 4a. Items 4b and 4c are independent and run in parallel off the Mac.
3. Risks and mitigations:
   - SEI changes the live bitstream: loopback decode proof, kill switch, default off if the proof fails.
   - LAN headroom may destabilise the estimate: default off unless the A/B is clean.
   - Merged moves may change the pointer feel: ≤ 1 tick, switch.
   - Queued host moves may change ordering: releases and clicks run synchronously after a drain.
