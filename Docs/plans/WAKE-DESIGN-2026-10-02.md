# Farside LAN wake design

**Date:** 2 October 2026
**Target:** Farside 1.0, aiming for approximately 27 October 2026
**Status:** Design only. Roshan authorized design research; implementation, builds, settings changes, device tests, helper deployment, and host installation are outside this authorization.

## Recommendation

The source baseline already has a Wake-on-LAN path through an awake Farside host. For 1.0, internet wake is realistic conditionally when the owner already has another paired Farside Mac awake on the target LAN, has locally registered the target on that helper, and the existing authenticated phone-to-helper session works over the route in question. This reuses the current host app and its owner registration; it does not require commissioning a new helper service, adding a router agent, or opening a public port. It is not a promise that a sleeping Mac can receive its own Internet request.

The phone does not send the broadcast. It sends a target ID over its active paired session; the awake helper emits one UDP magic packet on its selected LAN interface. A packet-send result is not evidence that the sleeping Mac woke. Keep the existing explicit helper setup, without adding a phone-side interface picker or extra wake options. Physical and security acceptance remain required before advertising 1.0 support.

## Existing source flow

1. The owner registers the sleeping target locally on the powered helper in Farside Availability settings. The saved record includes target durable host ID, helper durable host ID, the helper's current owner-pair grant, target MAC address, and helper interface name. It does not store an SSID or password. The settings view currently asks for the helper interface name (default `en0`); this is the existing local registration control, not a phone-side picker.
2. While the phone is connected to that helper, the helper advertises `wake.helper.1` only when there is an owner-pair-matching registration and the saved helper interface is currently available. The phone requires that negotiated feature, an active non-view-only session, non-concealed/non-PiP-background state, current host trust, and a user confirmation.
3. The phone sends only an opaque target UUID and a 32-character request ID over the existing control session. It does not send an IP address, MAC address, interface name, or arbitrary packet destination. The helper derives authority from its current paired-phone invitation and session, validates the request age and owner grant, resolves the UUID only in its local owner-registered store, and rechecks session/epoch authority and registration immediately before sending.
4. The helper discovers the current IPv4 address, netmask, broadcast address, and interface index for the locally registered interface name. The sender accepts only a valid private IPv4 broadcast configuration, binds UDP to that interface, enables broadcast, and sends one 102-byte packet to that interface's directed broadcast on UDP port 9. It does not scan for targets or mutate network settings.
5. The phone waits up to five seconds for a matching helper reply. The helper applies a 30-second request-freshness limit, an in-memory replay ledger scoped to the session/epoch, a one-packet-per-target-per-minute cooldown, and a 16-target store/active-send bound. After “packet sent,” the user ends the helper session and connects to the sleeping target. Only that target's own authenticated connection and fresh content establish availability.

The helper implementation uses BSD sockets. Apple's current TN3151 says Network framework does not support UDP broadcast. The saved interface name must still exist and be broadcast-capable when the request arrives. The current source does not persist an IPv4 prefix/broadcast profile or observed physical-support state, and does not refresh the target MAC from an authenticated connection to that sleeping target. Do not describe those future profile features as implemented. Keep the current interface mechanism as-is for this feasibility pass; do not add a phone-side interface picker or new options.

## Permissions and platform boundary

The current iPhone feature sends a control request over the already-established Farside peer session; it does not send UDP broadcast. Therefore the iOS multicast-networking entitlement is not a gate for this helper-based design. Apple's current TN3179 says macOS does not require that entitlement. The helper app still needs any applicable macOS Local Network privacy declaration/permission and sandbox UDP network capability; the source review here did not verify the built host's Info.plist, entitlements, permission prompt, or installed TCC state. Check those in the authorized implementation/release workflow without changing settings during this design task.

If Farside later returns to direct iPhone broadcast, Apple classifies UDP broadcast as a local-network operation and requires `com.apple.developer.networking.multicast` on iOS, with Apple's approval, plus `NSLocalNetworkUsageDescription`. Apple's TN3151 says Network framework does not support UDP broadcast. That alternative is outside this existing implementation. For the current path, keep the action foreground and user initiated; iOS background suspension is not a wake transport.

## Bonjour Sleep Proxy is a different path

Bonjour Sleep Proxy is LAN infrastructure that can preserve/advertise a sleeping host's Bonjour services and arrange to wake it when a client accesses a proxied service. It can help with service discovery and service access on supported networks. It is not the same operation as sending the raw `FF`/MAC WoL payload, is not an internet relay, and must not be assumed to exist on a user's router or subnet. The helper's direct WoL path must not depend on a Sleep Proxy. A future proxy-based service-access experiment should be measured separately from magic-packet wake.

## Mac support and practical limits

Apple's Remote Desktop guidance requires both network hardware that supports packet wake and the target Mac's “Wake for network access” setting. Apple documents Wi-Fi Wake on Demand on supported configurations, but that is not a promise for every Mac/router combination. The awake helper must have a usable broadcast interface on the target's LAN; a directed broadcast generally does not cross a router. A service proxy can affect service reachability but is not a replacement for this helper's packet send.

For a Mac laptop target, the best first feasibility case is the actual target on power with its lid open and one actual supported adapter, while the separate helper stays powered and awake. On battery, the available “Wake for network access” choice varies; “Always” permits attempts but does not guarantee reachability or acceptable battery impact. A closed lid is not a supported headless-use promise: normal closed-display operation depends on power and external display/input conditions, and a brief wake would not establish usable Farside capture. Sleep wake does not power on a shut-down Mac or recover a depleted battery. macOS may wake briefly to serve supported resources without restoring a usable Farside GUI session; Farside must prove fresh authenticated host readiness after wake.

Do not enable system settings, keep-awake assertions, or wake options silently. The owner must explicitly enable the target Mac's network-wake setting. The product should explain that actual support depends on the target adapter, helper interface, and network.

## Conditional internet wake using the existing helper

The current path can serve the internet-wake use case without a new helper deployment: the owner connects the phone to an already-awake paired Farside Mac, then that Mac broadcasts on its LAN to the locally registered target. If the existing peer session works from outside the home network, the helper is physically on the target's broadcast domain, and the target wakes and later accepts its own authenticated session, this is a plausible conditional 1.0 feature. The existing Farside session transport, whether direct or through an already-supported relay route, carries the peer connection; it is not asked to forward a LAN broadcast. If no such awake helper is available, internet wake is unavailable. The sleeping target never executes its own wake request.

Current source authorization is based on the active helper invitation's durable host ID and owner-pair grant, current peer/session identity, session epoch, connection deadline, and a parent authority lock around the final send. The local target registration must match the helper and owner pair. Requests are time-bounded and deduplicated in memory for the session; target sends are rate-limited. This is same-pair helper transport authority, not a separate web API.

Residual security gates remain before an end-to-end 1.0 claim. `WakeRequest` contains only a target UUID and random UUID-derived request ID; it has no per-request signature or MAC. The receiver relies on the existing paired Farside control-session authentication/integrity and live helper authority. Verify that the direct and relayed routes preserve end-to-end peer identity and confidentiality; do not infer this from local source structure alone. `targetHostID` is saved and format-checked during local owner registration, but the incoming request does not carry it and the helper does not compare it with a separately authenticated target-phone pairing. Local registration is therefore an owner's assertion that the MAC belongs to the intended target. The replay ledger is in memory and scoped to a live session/epoch; the 30-second arrival age, current session lease, and per-target cooldown bound that exposure, but are not a durable global nonce ledger. Replies are not separately signed; they rely on the same current peer session.

Do not add new network helpers, public port forwarding, target-side daemon installation, or router configuration for this 1.0 path. If the existing owner-registered helper is unavailable or its current route/security/physical evidence does not pass, retain the product's unavailable state.

## Source state inspected (not test evidence)

The implementation is present in the inspected checkout:

- [HostLANWake.swift](../../RemoteHost/Availability/HostLANWake.swift#L3-L16) builds the exact 102-byte magic packet; lines 24–37 bind each target record to target/helper host IDs, helper owner-pair ID, MAC, and interface name. Lines 51–78 store up to 16 explicit local owner registrations and fail closed on unreadable data. Lines 81–122 apply current helper authority, a 30-second request age, a session/epoch-scoped in-memory replay ledger capped at 128 IDs, and a one-target-per-minute cooldown.
- [LANMagicPacketSender.swift](../../RemoteHost/Availability/LANMagicPacketSender.swift#L4-L38) derives the helper interface's current private IPv4 address/netmask/broadcast from `getifaddrs` for the registered name. Lines 42–74 bind a BSD UDP socket to that interface and send exactly one datagram to its computed directed broadcast on port 9. It reports `.sent` when the kernel accepts the datagram, not when the target receives it.
- [WakeTargetRegistrationView.swift](../../RemoteHost/Availability/WakeTargetRegistrationView.swift#L15-L63) is the existing helper-side owner registration UI. It asks the owner to enter the target host ID, MAC, and helper interface name locally, defaults the interface field to `en0`, and provides an explicit confirmation. It does not automatically discover or verify the target MAC against a live target session.
- [HostModel.swift](../../RemoteHost/HostModel.swift#L2904-L2924) derives helper/owner authority from the active invitation and current session, then rechecks peer identity, pairing, active state, epoch, lease, view-only/lock/pause state, and the input authority lock around the send. Lines 3007–3036 advertise `wake.helper.1` only when a matching local owner registration and current interface exist.
- [WakeRequest.swift](../../RemoteShared/WakeRequest.swift#L3-L20) carries only a target UUID and request ID. [ControlProtocol.swift](../../RemoteShared/ControlProtocol.swift#L305-L317) validates the wake action extension shape. [RemotePhoneApp.swift](../../RemotePhone/RemotePhoneApp.swift#L191-L225) gates the request on the negotiated feature and active session, matches its reply to request/host/session/epoch, and labels `.sent` as unconfirmed target wake. [LANWakeView.swift](../../RemotePhone/LANWakeView.swift#L8-L27) requires the owner to connect to a powered helper, enter the locally registered target ID, and confirm the send.

The source does not store the target network prefix, target broadcast address, observed/tested hardware-support state, or SSID secrets. It derives the helper broadcast at send time and never reads the SSID in this path. The helper stores `targetHostID` but does not use that value to authenticate the target at request time. The source view has a local interface-name field; no phone-side interface picker is part of this design.

[`LANWakeTests.swift`](../../RemoteTests/LANWakeTests.swift#L14-L103) contains fixtures for packet bytes, directed-broadcast validation, unsupported interfaces, request freshness/replay/cooldown, owner binding, removal/expiry rechecks, store preservation, and action schema. These tests were inspected but not run for this design update. Their presence is not a pass result and does not prove network, entitlement, service, or hardware behavior.

## Evidence required for a 1.0 claim

First verify the built helper's Local Network privacy declaration/permission and any sandbox UDP network entitlements; this source review did not inspect signed build metadata or live permission state. Confirm that the direct and relayed phone-to-helper routes retain authenticated end-to-end peer identity and confidentiality. The wake code inherits the existing paired control session and does not add a request signature/MAC; the helper registration's `targetHostID` is a manually entered owner assertion, not a target-side pairing proof.

Then test with the actual phone outside the home network, an already-awake owner-paired helper on the same LAN as the target, and the actual sleeping target Mac/adapter. Confirm owner-local target registration, helper interface availability, packet-send status, whether the target wakes, and whether its own authenticated Farside session returns fresh usable content. Repeat only the power/lid/adapter combinations the product intends to support; separately record Wi-Fi and any intended Ethernet dock, power adapter/battery, lid open/closed, Wake for network access, subnet changes, and negative cases such as client isolation or shutdown. The helper must remain awake for the entire request. A unit fixture, packet-send log, Bonjour listing, or successful session to the helper is not physical target-wake evidence.

Acceptance is per helper interface, target adapter, network, power, and lid condition. If only one measured configuration passes, limit 1.0 wording to it. Without route/security and physical target-wake evidence, make no success claim; retain the unavailable or awake/unlocked requirement for unsupported cases.

## Apple sources checked 2 October 2026

The live Apple documentation and release notes below were checked on 2 October 2026. Apple's iOS 27 and macOS 27 release-note Markdown endpoints were fetched; focused searches found no wake-specific guarantee that changes the limits above. Current framework guidance comes from Apple's TN3151/TN3179 and entitlement/property-list documentation. The Sleep Proxy architecture source is explicitly historical (2013).

- [TN3179: Understanding local network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) — Local Network permission, broadcast classification, iOS multicast entitlement and macOS distinction, interface-name warning, and Bonjour declarations.
- [TN3151: Choosing the right networking API](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api) — UDP broadcast is unsupported by Network framework; BSD sockets are the documented alternative; multicast entitlement and local access requirements.
- [Multicast networking entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.multicast) — required for iOS broadcast/multicast and requires Apple's permission.
- [NSLocalNetworkUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nslocalnetworkusagedescription) — required user-facing reason for local network operations.
- [Apple Remote Desktop: wake a computer](https://support.apple.com/en-sg/guide/remote-desktop/apd5535ee19/mac) — packet-capable network hardware, Wake for network access, Wi-Fi Wake on Demand check, and subnet/Sleep Proxy limitation.
- [Share Mac resources during sleep](https://support.apple.com/en-nz/guide/mac-help/mh27905/mac) and [sleep/wake settings](https://support.apple.com/en-gb/guide/mac-help/-mchle41a6ccd/mac) — service wake behavior and power-dependent settings.
- [Closed-display mode on Mac](https://support.apple.com/en-ie/102501) — conditions for supported closed-display use.
- [iOS background execution sequence](https://developer.apple.com/documentation/uikit/about-the-background-execution-sequence) — background tasks can be suspended; no persistent arbitrary UDP execution guarantee.
- [OS X Mavericks Core Technologies Overview (2013)](https://www.apple.com/media/us/osx/2013/docs/OSX_Mavericks_Core_Technology_Overview.pdf) — historical Bonjour Sleep Proxy overview; used only for the mechanism distinction, not modern router coverage.
- [macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes) and [iOS/iPadOS 27 release notes](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-27-release-notes) — fetched 2 October 2026; no relevant wake guarantee surfaced in focused searches.
