# PocketDesk remote prototype contract v1

**Engineering draft, subordinate to [PRODUCT.md](../PRODUCT.md).** Private feasibility implementation is active. Existing protocol choices remain subject to live validation; this file is not a second product specification.

User decision: built-in away-from-home access, iPhone 17 and M4 MacBook Air, awake/unlocked host acceptable during prototype. WebRTC provides media, ICE/STUN/TURN and reliable ordered data channels. WSS signaling is a rendezvous path, not authority to view/control. No Tailscale dependency. Native app uses normal system TLS verification and rejects insecure non-loopback signaling URLs.

## Signaling routing

JSON, version 1. WSS `/signal`, TLS terminated by deployment reverse proxy. Local development binds 127.0.0.1; ws is allowed only for localhost/127.0.0.1/[::1]. No credential in query strings. Max record 256 KiB; no compression; bounded sends. First record within five seconds:

Host: `{ "type":"register", "version":1, "role":"host", "room":"<64 lowercase hex SHA256(hostToken UTF8)>", "token":"<64 lowercase hex random 256-bit hostToken>", "clientTokenHash":"<64 lowercase hex SHA256(clientToken UTF8)>" }`

Client: same fields with `role:"client"`, token is clientToken, no clientTokenHash. Server checks host room hash, holds clientTokenHash while host online, compares client digest before admission. Only one host/client socket per room; duplicates do not evict existing peers. Unknown/offline host fails. Host reconnect registers anew. Server stores hashes only and does not log messages/tokens. This authenticates routing, NOT screen access.

Server response `{ "type":"registered", "role":"host|client" }`, then optional `{ "type":"ice", "servers":[{"urls":["turn:..."],"username":"...","credential":"..."}] }`. Configured TURN credentials come from the selected Cloudflare API adapter or coturn shared-secret adapter, expire, and never expose the long-lived issuer secret to apps. No configured TURN means direct-only test coverage, not reliable public connectivity.

The `ice` message may carry an optional `"policy":"relay"` (test-only service setting `POCKETDESK_TEST_FORCE_RELAY=1`; absence means `all`). A native peer that receives `policy:"relay"` builds its peer connection with relay-only ICE and, if no `turn:`/`turns:` server was delivered, fails closed instead of connecting directly. Any other `policy` value is a protocol error. Older peers ignore the field and connect normally, so a forced-relay test needs updated apps on both devices. The phone's local Relay-only toggle remains an independent way to force relay on that side only.

Session renewal (30 September 2026, capability `renew.1`). A room is a lease, not a fixed lifetime. A peer that supports renewal adds `"features":["renew.1"]` to `register` (older services ignore unknown fields). The service answers only such peers: `registered` carries `"renew":{"version":1,"leaseSeconds":1800,"renewAfterSeconds":900,"credentialSeconds":3600}` (`credentialSeconds` only when a relay provider is configured). After `renewAfterSeconds` the peer sends exactly `{"type":"renew"}`. The service replies `{"type":"renewed","leaseSeconds":1800,"renewAfterSeconds":300}` and, once the peer's credentials are a third of their TTL old, adds `"servers":[...]` and `"credentialSeconds"`. A refresh that could not be issued adds `"code":"relay_unavailable"|"rate_limited"|"renewal_pending"` and a shorter `renewAfterSeconds`; the lease is still extended. Either peer of an approved room may renew and any renewal extends the room to a full lease from that moment; a lease that has already lapsed is never extended; approval is re-checked on every renewal. A peer that did not negotiate the feature is never sent the new messages and gets `invalid_message` if it sends `renew`, so old apps and old services keep the original messages, and a room in which nobody renews keeps the original fixed lifetime (one renewing peer keeps it alive). On receiving fresh servers an app applies them to its live peer connection with `setConfiguration` (no media change). The host then restarts ICE, only when the selected route is a relay, so the media moves to a new relay allocation while the old one keeps carrying it; both sides answer through the ordinary encrypted `media` signal, and a signaling failure at that moment falls back to the existing reconnect. Details and evidence: [SESSION-LENGTH-FIX.md](research/2026-09-28-round2/SESSION-LENGTH-FIX.md).

Remote access (29 September 2026, capability `remote.1`, additive; served by `Backend/`, see `Backend/ENTITLEMENT-CONTRACT.md`). PRODUCT D28 requires free use to stay on the same network. Current server enforcement withholds managed STUN/TURN: a room whose phone has not proved a subscription receives `ice` with `"servers": []` on both sides. This does not prevent public or VPN direct candidates inside opaque signaling; native route enforcement remains a release blocker. A phone that supports the paid path adds `"remote.1"` to `register.features` and, when it holds one, `"entitlement": "<token from POST /v1/entitlements/verify>"`. Peers that listed `remote.1` get `"access": "remote" | "local"` on `registered`. When the phone's token is valid the service issues STUN and short-lived TURN to both peers: the phone in its `ice`, the Mac in a second `ice` message sent immediately before `peer` `online:true` (the Mac registers first and applies whatever `ice` it last received when the handshake starts). A phone that listed `remote.1` without a valid token receives a **non-closing** `{ "type":"error", "code":"entitlement_required" }` before `registered` (`access:"local"`) and `ice` (`servers:[]`); the session proceeds locally and the phone should re-verify and reconnect. `renewed` may carry `"code":"entitlement_required"` with no `servers` when the subscription lapsed mid-session (the lease is still extended; the session lasts until the credentials in use expire). A refund, revocation or operator block closes both sockets with reason `entitlement_revoked` or `room_not_approved` and revokes every issued credential. When the entitled phone leaves, the Mac receives `ice` with `"servers": []` after `peer` `online:false`. The service may repeat a peer's most recent `ice` message unchanged as a keepalive (off by default); peers treat it exactly like the first. Transient service problems (room unreachable, creation limit, byte budget) close the socket without an error frame (code 1013, reason `busy` or `rate_limited`) so the existing reconnect handles them. Phones that do not list `remote.1` never receive the new field or codes and simply get `servers: []`. Room approval is automatic: a host whose token hashes to its room is admitted; there is no operator CLI in the Cloudflare service.

Peer state `{ "type":"peer", "online":true|false }`. Both peers are notified when counterpart joins. Host disconnect closes its client. Client disconnect notifies host and keeps host registration. Client-to-server `{ "type":"signal", "payload":"<base64 opaque sealed bytes>" }` forwards only to authenticated counterpart in that room. Error `{ "type":"error", "code":"..." }` with sanitized reason. No SDP, ICE, remote input or video parsed by signaling service.

## Endpoint authentication and session binding

Pairing must authenticate WebRTC negotiation end to end; TLS/DTLS alone does not protect against a malicious signaling service substituting SDP. Native peers protect signaling payloads with CryptoKit AES-GCM using a random per-pair key never sent to the signaling service. The complete SDP including DTLS fingerprints and all ICE candidates are inside authenticated payloads. Reject tampered messages. Fresh client request and host challenge nonces bind every negotiation; only a response to the current challenge can start a session. Messages carry session ID and sequence; reject duplicates, old sessions, unexpected message types and oversized plaintexts. Local host authorization precedes initial pairing/capture/input. Pairing persists in device-only Keychain, is revocable, and must not put reusable credentials in logs.

WebRTC input travels on one reliable ordered `control` data channel. Every message has version/session/sequence; pointer events include geometry epoch. Explicit button down/up and releaseAll are idempotent. A two-second host held-input lease is renewed only by accepted drag/move activity, never by heartbeats; expiry releases the hold and tells the phone to reset drag state. No queued clicks or text replay after reconnection. Capture begins only after endpoint authentication and authorized host content selection. Video never gates input on a per-frame acknowledgement.

This freezes server routing now. Native enrollment/session/input schemas must be finalized and tested before screen/input authorization; the paragraphs above are requirements, not a claim of completed implementation. This protocol supersedes the attachment's LAN-only transport proposal for the current user-selected goal.

## Implemented private control envelope

`ControlPacket` contains version 1, fresh session ID, monotonically increasing sequence, and `RemoteAction`. The host sends `geometry` with logical width/height in x/y and a new epoch before `viewing`. Phone user actions carry that epoch; the host rejects stale epochs. Release is always accepted. Display changes end the session instead of silently retargeting input; the one exception is a switch the phone itself asks for (below), which also starts a new epoch.

Phone parity capabilities (29 Sep 2026). The host lists them in `capture.features`; a phone sends the new actions and names only after seeing the matching feature, because older hosts end the session on unknown actions and would misread new fields. `pointer.absolute.1`: `moveTo` places the pointer at display-local logical points x/y (0…geometry size, clamped; negative is invalid), carries the usual native envelope and `pointerSync.move` ordinal, and drags while a hold is active; click counts may be 3 directly after a count-2 click at the same place; `modifiers` on pointer actions become mouse-event flags (hardware ⌘/⇧/⌥/⌃ clicks). `pointer.middle.1`: `middle` is a centre-button click at the pointer (count 1 only, never during a hold). `keys.extended.1`: `key` accepts digits, punctuation, F1–F20, Home/End/Page Up/Page Down/Forward Delete/Help, keypad and JIS keys by position; the host adds the Fn or numeric-pad flag a Mac keyboard would. Phones repeat held keys themselves (0.5 s, then every 70 ms) so a lost connection can never leave a Mac key down. `display.select.1`: the phone sends `displays` (no fields) and the host answers `displays` with up to 16 `{id, name, width, height, pixelWidth?, pixelHeight?, main}` and the streamed `display`; `display` with `display: id` asks to stream another display, which the host honours only for a known display, only while control is allowed (choosing what the Mac shares needs the same authority as controlling it), by releasing held input, advancing the epoch, resending `geometry`/`viewing`/`capture` and restarting capture within the same session; every request is answered with the list, and `capture` carries the streamed `display`. The phone remembers the choice per Mac (keyed by a hash of the pairing room) and asks for it again on the next connection.

`capture` x=1/0 reports source health. Only fresh complete/idle ScreenCaptureKit status permits retransmitting the last frame; retransmission itself never refreshes capture health. Phone input requires both frame freshness and capture health. Live idle-status cadence remains a manual test.

`text` uses a request ID in key (at most 32 UTF-8 bytes), with payload bounded by both 4096 UTF-8 bytes and 1024 UTF-16 units. `textResult` echoes key and x=1 if input was accepted for OS injection or x=0 if refused. This is not proof an application used the text. The phone retains its draft until the matching receipt and never automatically retries uncertain text.

Pointer telemetry v1 (28 Sep 2026) rides in an optional `pointerSync` envelope that older peers ignore. The host advertises it with `videoCursor` on `capture`; a supporting phone answers on every `heartbeat` (`overlay` true only while it holds fresh telemetry) and tags each `move` with a per-epoch ordinal. Only then does the host send the new `pointer` action (display-local x/y, visibility, shape name, last applied move ordinal, sample counter, `videoCursor`), because older phones end the session on unknown actions. The host omits the cursor from capture only after the phone requests an overlay, reports `videoCursor:false` from the moment hiding is requested and `true` only once showing is applied, and restores the cursor on stale heartbeats or any new capture. Unknown shape names draw as the arrow. Design and evidence: [pointer report](research/2026-09-28-round2/POINTER-REPORT.md).

File transfer v1 (`file.1`, 30 Sep 2026; design: `research/2026-09-30/REMOTE-UNLOCK-AND-FILE-TRANSFER.md` Part B). Native hosts open a second ordered, reliable data channel labelled `file` beside `control`; older phones close it and keep their session, and the browser peer never gets one. A phone uses file actions only after seeing `file.1`. Control frames ride `control` as `RemoteAction(action: "file", file: {version 1, op, transfer, …})` with `transfer` = 32 lowercase hex: `offer{name ≤255 B, bytes 1…1 GiB, type?}`, `accept`, `progress{bytes}` (receiver, ≤4 Hz), `complete{digest}` (sender, after the last chunk; SHA-256 hex), `result{status}`, `cancel`, `request` (phone asks the Mac to show an open panel; the Mac answers with an `offer` reusing the same transfer id, or a `result`), and `link{url}` (http/https ≤2 KB; the Mac copies it and shows an Open panel, never opening by itself; `result` `offered`/`copied`). Statuses: `stored cancelled tooLarge notAllowed disabled busy diskFull denied invalid timedOut empty unsupported unreadable offered copied`; unknown codes read as failure. Bytes ride `file` as binary `FSF1 | 16-byte transfer id | UInt64 BE offset | payload`, contiguous from offset 0. Receivers take messages up to 64 KiB. Senders use 64 KiB messages and keep up to 2 MiB of `bufferedAmount` (refilled from buffered-amount callbacks at half) only on a calm selected LAN pair with the video ladder at rung 0 and a peer SDP `max-message-size` of at least 64 KiB (or 0); any queued input pauses admission and a ladder step or RTT rise falls back to 16 KiB messages, a 32 KiB queue and the measured allowance (DF10, 1 Oct 2026; internal kill switch `farsideFileFastLaneDisabled`). Relayed bytes keep 16 KiB messages and the relay pacing. The receiver writes a hidden `.farside-<id>.partial` (create-exclusive, no symlink follow), renames only after the digest matches and never over an existing name (`name 2.ext`), and deletes the partial on any failure. The phone accepts an `offer` only for its own pending `request`. The Mac admits transfers only in the current, unpaused session and refuses them (`disabled`) while sharing a view-only scope; there is no Mac setting (MS05, 1 Oct 2026; a stored `allowFileTransfer` value is ignored) and control authority is not required. Mac files land in `~/Downloads/Farside` with the quarantine attribute; phone files land in the app's Documents (Files › On My iPhone › Farside). Only a `diskFull` code crosses the wire, never free space. Names and contents are never logged. Transfers are foreground-only, one each way, no resume; a phone backgrounding or a session ending cancels and deletes partials.

For first enrollment, the host saves rotated trust before sending it to the approved phone. The old invitation is not a recovery credential. An interrupted enrollment that fails to save the new phone trust requires a fresh pairing code beside the Mac. Existing sessions protect negotiation with the original cipher until they finish; reconnect uses rotated credentials.

The relay-only option restricts ICE policy to TURN. Diagnostic route/codec/fps/network RTT comes from WebRTC statistics; network RTT is not physical input-to-visible latency. Test receipts distinguish generated media from real ScreenCaptureKit capture.
# Browser v1 implementation contract — 13 September 2026

This separate namespace preserves native pairing and `/signal`. Initial service binds loopback only. HTTPS/private proxy support must preserve exact Origin and Host checks; public deployment is paused.

## Canonical browser crypto

`BrowserCrypto.canonical(fields)` is UTF-8 `PocketDesk/browser/1` followed by each UTF-8 string field, each prefixed with its unsigned 32-bit big-endian byte length (the domain is prefixed too). No JSON canonicalization. P-256 signing public keys are 65-byte raw X9.63, signatures 64-byte P1363; binary values use standard padded base64. IDs/nonces/tokens are 32 random bytes represented as 64 lowercase hex characters. Times/revisions/sequences are canonical nonnegative decimal strings (at most JavaScript safe integer). Signed fields have fixed order; no optional fields.

Enrollment offer `pocketdesk-browser:` + base64 JSON contains `{version:1,url,hostID,hostKey,secret,expires}`. It is created explicitly on the Mac, valid 120 seconds, and is pasted into an inert browser field, never a URL. Browser creates a non-extractable P256 signing key in IndexedDB. Enrollment POST carries only `{nonce,payload}`: nonce is 12 random bytes, payload is AES-256-GCM ciphertext plus 16-byte tag for UTF8 JSON `{peerID,publicKey}`. The AES key is the offer's 32-byte random secret (hex decoded); AAD is canonical `["enroll",hostID,origin]`. The secret is never sent through the relay. Mac decrypts using its live offer and validates all fields before approval. Browser requires offer origin to exactly match its trusted viewer origin. Mac requires explicit approval (synthetic harness may explicitly auto-approve invented content only), consumes the offer, and stores a separate BrowserPeer. Response `{receipt,signature}` signs fields `["enrolled",hostID,peerID,publicKey,origin,mode,display]`. Browser pins offer hostKey before accepting receipt. Separate Keychain namespace for host signing identity and browser peers; no native pair mutation.

Challenge POST `{peerID,nonce,mode}`. Mac returns `{fields,signature}` signing exactly `["challenge",hostID,peerID,origin,mode,display,revision,session,expires,nonce,hostNonce,hostEphemeralPublicKey]`. Challenge lasts 30 seconds; fresh P256 ECDH ephemeral key each time. Browser validates all pinned/request fields, then proof POST `{session,publicKey,signature}` where publicKey is its new ephemeral key and signature signs `["proof",SHA256(canonical(challengeFields)),publicKey]`. Mac atomically consumes the pending challenge before accepting proof. One active/pending browser session, reject busy; do not evict native sessions.

Both endpoints derive AES256 key from ECDH using HKDF-SHA256, salt SHA256(canonical(challengeFields)), info UTF8 `PocketDesk/browser/1/signaling`. Host response `{ticket,session,expires,signature}` signs `["ticket",session,ticket,expires,challengeHash]`; expires is ticket deadline (15 seconds). Before responding the host installs `{type:"ticket",ticket,session,expires,peerID}` into its authenticated service connection. Service retains only ticket SHA256; consumes atomically on first redemption. Session maximum 10 minutes is enforced independently by Mac. Expiry/Stop/revoke clear challenge, ticket and media.

## Service transport

Dedicated `createBrowserService` runs independently of native createService. Host WSS `/browser-host` rejects Origin, first message `{type:"host",hostID,token}` where SHA256(token)==hostID; bounded peers and registration timeout. Browser HTTP `POST /browser-api/<hostID>/<enroll|challenge|proof>` checks exact configured Origin/Host and JSON/size, forwards `{type:"request",id,operation,body}` to the authenticated host. Host replies `{type:"response",id,body}` or `{type:"response",id,error}`. Enrollment requests last up to 120 seconds for human approval; challenge/proof requests last five seconds. Timeout or HTTP cancellation sends `{type:"cancel",id}` to the host; only matching pending authority is cleared. Late authenticated responses are ignored after cancellation, rather than disconnecting the host. Requests also cancel when the host/socket stops. GET is static/inert. No endpoint mints credentials on GET.

Browser WSS `/browser-signal` checks exact Origin, receives only `{type:"browser",hostID,session,ticket}` before admission. Service consumes ticket before attaching one browser, sends host `{type:"joined",session}`, browser `{type:"registered",session}`. Host/browser relay `{type:"signal",session,envelope}` only in attached session. End `{type:"end",session}` closes that session; host Stop/disconnect invalidates all pending transport authority. Service never sends ICE/session payload before authentication. Native routes remain unchanged.

Envelope `{sequence,direction,payload}` contains base64 AESGCM ciphertext+tag. Sequence starts at 1 and strictly increases, direction `host` or `browser`. Nonce UInt32BE(1 host/2 browser)+UInt64BE(sequence); AAD canonical `["signal",session,direction,sequence,challengeHash]`. Decrypted UTF8 JSON is MediaSignal. First browser signal is `{kind:"ready"}` for key confirmation; host then offers. Offer/answer SDP and ICE are all encrypted/authenticated. DTLS fingerprint in authenticated SDP binds media. The established ordered binary `control` channel receives a first `{type:"bind",session,challengeHash}` packet; its DTLS identity is already bound by authenticated SDP. No input before this binding.

## Control and displayed-frame proof

Separate binary UTF8 JSON `{type:"input",session,sequence,revision,frameToken,action}`; action follows RemoteAction bounds. OS actions require interactive grant, separate Mac consent, current Accessibility, current capture health and revision, strict input sequence, plus a known per-frame token no more than 600ms old by host monotonic time. Token is carried only in pixels, never status messages. Release bypasses freshness/scope to release only this session's held input. Unknown/malformed/replayed input closes or rejects and releases held state. Text acknowledgements retain existing explicit result semantics. On source/capture-health change clear token ring and release. Existing native input is unchanged.

Row-major: fixed sync 0x50444231 (32 bits), version 1 (8 bits), random token (128 bits), CRC32C(version byte+token bytes) (32 bits). Browser reads intrinsic decoded pixels in requestVideoFrameCallback. Host stores token+revision+monotonic time in a 128-entry ring. Compression damage blocks input. This establishes a conservative frame delivery/decode/return bound, not human attention or exact latency. Footer must not cover source content. Browser metadata remains diagnostics, not freshness authority.

Current physical Safari/Chrome, native-to-browser marker survivability, real capture/input and public TURN gates are unvalidated. Contract receives independent review before real access.


### Browser-code delivery trust boundary

Enrollment encryption prevents an untrusted **forwarding path** from substituting the browser key when the user runs the trusted viewer. It cannot protect a secret typed into malicious JavaScript. This local feasibility process serves both static viewer files and signaling, so the local code and its delivery are trusted. A compromised static-content origin can replace the client and defeats browser confidentiality/control regardless of transport crypto. Public G4 remains blocked pending an independently reviewed trusted static-delivery and signaling-origin design; these local passes do not close that deployment threat. No public service is authorized by this checkpoint.

## Browser ICE delivery and relay enforcement — contract frozen 15 September 2026

Parent-owned. Extends the browser admission contract above; native `/signal` behavior is unchanged.

1. **Issuance point.** Only after `registerBrowser` has atomically consumed a valid ticket and created the `BrowserSession`. Never on static GET, `/browser-api/*`, or before admission. The service calls the existing `TurnCredentialProvider.issue({ room: session, role })` once for `role: 'host'` and once for `role: 'browser'`, through a bounded issuer (per-process sliding 60 s cap `issuesPerMinute`, `Promise.race` timeout `timeoutMs`, ≤8 servers / ≤8 URLs each). The browser service keeps its own budget; it is a separate process from native `/signal`.
2. **Messages.** Before `joined` reaches the host, service sends on `/browser-host`: `{ "type": "ice", "session": <hex32>, "servers": [ICEServerConfiguration], "policy": "all" | "relay" }`. Before any `signal` is relayed to the browser, service sends on `/browser-signal`: `{ "type": "ice", "servers": [...], "policy": "all" | "relay" }`. `ICEServerConfiguration` is the existing native shape (`urls`, optional `username`, `credential`). Exactly one `ice` per session per side; a duplicate or mismatched session is a protocol error.
3. **No relay configured.** Service still sends `ice` with `servers` = configured STUN only (possibly empty) and `policy: "all"`. Clients always wait for `ice` before constructing a peer connection (bounded by the existing admission timeout; timeout → fail closed with `ice_timeout`).
4. **Issuance failure.** If a relay provider is configured and issuance fails or times out, the session ends with `error: relay_unavailable` to the browser and `end` to the host. No silent downgrade to direct-only.
5. **Test-only relay enforcement.** Service config `testForceRelay` (env `POCKETDESK_BROWSER_TEST_FORCE_RELAY=1`) sets `policy: "relay"`. Startup refuses `testForceRelay` without a relay provider. Browser: `new RTCPeerConnection({ iceServers, iceTransportPolicy: policy })`. Mac: `PeerMedia(isHost: true, servers:, forceRelay: policy == "relay")`. Either side receiving `policy: "relay"` with no server carrying a `turn:`/`turns:` URL fails closed (`relay_required_unavailable`). Diagnostics report the selected pair type. The selected route is the evidence; the policy alone is not.
6. **Revocation.** Service stores issued servers per session and per role. `endSession`, host `stop`/`end`, browser `end`, either WS `close`, host authority stop, and `service.stop()` revoke each role's credentials exactly once (idempotent guard) when the provider supports revocation. Late issuance results that arrive after the session ended are revoked immediately. Shutdown drains revocations within a bounded deadline. Credential TTL expiry remains the backstop.
7. **Secrets.** TURN key tokens stay server-side. Issued short-lived credentials appear only in the two WS messages above, never in logs, diagnostics reports, receipts, or URLs.
8. **Public route allowlist (production entrypoint).** Exposed: viewer static assets (`/`, `/app.js`, `/style.css`, `/src/*`), `/browser-host`, `/browser-signal`, `/browser-api/:hostID/{enroll,challenge,proof}`, and later `/mcp` plus the OAuth metadata/authorize/token routes. Not exposed in production: `/probe/*`, `/fixtures/*`, `/api/diagnostics` (config `devRoutes: false` → 404).

## Chat MCP integration — contract frozen 15 September 2026

Parent-owned. One shared authenticated MCP backend with thin ChatGPT/Claude presentation adapters. Research: `outputs/chat-integration-research-2026-09-15/mcp-platform-requirements.md` (several host facts marked unverified; verify live before claiming host support).

**Placement.** `Server/src/mcp/**`, mounted in the browser service process under the same origin at `/mcp`, `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`, `/oauth/authorize`, `/oauth/token`, `/oauth/register`, `/oauth/revoke`, `/mcp-ui/*` (widget assets). Official TypeScript MCP SDK, Web-Standard Streamable HTTP transport (stateless-capable, with session fallback until both hosts are verified). Codex app-server is never reachable from these routes.

**Authorization server (single owner, self-hosted).**
- OAuth 2.1: authorization code + PKCE S256 only; `plain` and implicit rejected. RFC 9728 protected-resource metadata; `WWW-Authenticate` on 401 names it. RFC 8414 AS metadata advertises CIMD (`client_id_metadata_document_supported: true`, `token_endpoint_auth_methods_supported: ["none"]`) and a DCR `registration_endpoint` as a bounded fallback (per-minute cap, client records expire if never authorized).
- CIMD fetch: HTTPS only, bounded size/time, no redirects to private addresses, cached briefly. Redirect URIs must exactly match the client's registered/metadata list. Known hosts: `https://claude.ai/api/mcp/auth_callback`, `https://claude.com/api/mcp/auth_callback`. ChatGPT's callback comes from its metadata/registration, recorded after the live check.
- **Owner binding by explicit local approval.** `/oauth/authorize` validates the request, then asks the Mac host over `/browser-host` (`request` op `mcp_authorize`, carrying client display name, redirect host, and a 6-character confirmation code, never tokens). The authorize page shows the same code and waits. The Mac shows Approve/Deny with the code, client name, and redirect host. Deny, host offline, or 120 s timeout → `access_denied`. Only an approval mints a single-use authorization code (60 s) bound to hostID, client_id, redirect_uri, PKCE challenge, and `resource`.
- Tokens: opaque 32-byte random values, stored only as SHA-256 hashes in a mode-600 private file outside the repo. Access token TTL 1 h with audience = this server's `/mcp` resource. Refresh tokens are issued only with `offline_access`, rotate on every use, and reuse of a rotated token revokes the whole grant. The grant expires after 30 d idle. The Mac lists MCP grants and can revoke them (host message `mcp_revoke_grant`), and `/oauth/revoke` works too. Revocation is immediate for all tokens of that grant.
- MCP identity is separate from browser enrollment: no MCP token can admit a browser, and no browser credential can call MCP.

**Server-side authorization on every operation.** Each tool resolves grant → hostID and checks the grant is live. Scopes: `desktop.access` (request/status/stop) and `screen.inspect` (inspection tool only; still requires a separate Mac-side inspection grant).

**Tools.**
| Tool | Behavior |
|---|---|
| `request_desktop_access` | Creates an *access intent* (random ID, 10 min TTL, owned by the grant). Returns `{ viewerURL, readiness, intentID, expiresAt }`. `viewerURL = <origin>/?intent=<id>` is inert: opening or prefetching it grants nothing, and the page still requires existing browser enrollment plus human Connect plus the Mac admission policy. Readiness comes from host status: `host_offline`, `permissions_missing`, `display_not_selected`, `browser_access_disabled`, or `ready`. |
| `session_status` | For the caller's intents only: readiness, `connection` (`none`/`connecting`/`connected`/`ended`), `scope` (`view`/`control`), active inspection grant summary, and actionable failure codes. |
| `stop_session` | Ends only a browser session admitted through one of the caller's intents, via host `stop` for that session. Idempotent: an unknown or ended session returns `{ stopped: false, alreadyEnded: true }`. Never touches native sessions or other intents. |
| `inspect_screen` | Requires `screen.inspect` scope AND an active Mac-created inspection grant: selected display (optionally a region), expiry ≤ 15 min, a visible Mac indicator while active, and a revoke action. Returns one fresh frame (JPEG, bounded size, captured after the request) plus capture time. Errors: `inspection_not_granted`, `inspection_expired`, `host_offline`. Tool description and Mac UI state that frames enter the receiving model's context. Human viewing never implies this grant. |

Tool results never carry continuous video, input events, enrollment secrets, TURN credentials, or raw addresses.

**Presentation adapters (T1–T3 per host).**
- T1 external: tool result text plus link; the host opens `viewerURL` in the system browser → existing full-control browser path.
- T2 embedded view: `ui://pocketdesk/viewer` MCP Apps resource (`text/html;profile=mcp-app`; add ChatGPT legacy `_meta["openai/outputTemplate"]` / `openai/widgetCSP` only if the live check needs them). CSP `connectDomains` = service origin (HTTPS + WSS), `resourceDomains` = service origin. The widget runs its own separate browser enrollment in its sandboxed origin (never shared with the external browser), is view-only by default with local zoom/pan, and has an "Open to control" action (`ui/open-link` / `openExternal`) to `viewerURL`.
- Moving embedded view → external control: the widget ends its own session before opening the link, and the external page requires a fresh Connect. The service's one-active-viewer policy rejects a second admission with `viewer_busy` rather than silently evicting.
- T3 embedded control: same widget with the control scope enabled only when that enrollment was approved for control on the Mac. Pointer, typing/IME, layout, and interruption are verified per host. Where unsupported, T3 is recorded as pending and T1 is the fallback.
